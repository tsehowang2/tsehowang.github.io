Tools functions workflows and agents

Tutorial 27Test your understanding
Lecture slides · Week 27

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

A calculator is a useful concrete capability

A bus ticket costs 4 dollars and a child ticket costs 2 dollars. Two adult tickets and one child ticket cost 2×4+1×2=10 dollars. A deterministic calculator can check the arithmetic.

The model can suggest an expression, but application code decides which operations are available and validates the arguments. A generated function name does not create permission to execute arbitrary code.

Start with this narrow capability before discussing an agent framework. A tool is an interface to a specified operation with a contract.

Start with an example

A tool call has a name arguments and a result

A proposal might be name=calculate, arguments={expression:"2*4+1*2"}. The controller validates the shape and expression, runs the bounded arithmetic operation, and returns value=10.

The observation is then available to form the response. The final answer should agree with the result and, if necessary, cite the source of the ticket prices.

Code execution on the website is unnecessary for learning this control flow. The visual lesson simulates it, while the notebook runs the actual bounded reference implementation.

Build the mechanism

Schemas make the boundary inspectable

Define required keys, allowed types, ranges, and extra-field behavior. An integer timeout field should not accept true merely because Python treats bool as a subclass of int.

A configuration validator can accept a well-formed invocation but return valid=false because the proposed timeout is out of range. That differs from rejecting a malformed call.

Error categories help debugging: proposal parsing, schema failure, scope failure, execution failure, domain-invalid result, and final-answer error.

Build the mechanism

A fixed workflow

For a simple ticket task, a workflow can retrieve the current prices, calculate a total, and format a response in a predetermined order.

The model may help extract a structured request, but the control path remains largely fixed. This can be easier to test and sufficient for the task.

Do not add adaptive planning unless a task actually benefits from choosing the next action based on observations.

Build the mechanism

An agent chooses actions adaptively

For troubleshooting, the next step may depend on a result: inspect the requested version, retrieve a rule, validate a configuration, and investigate the first violation.

An agent lets model outputs influence the next action. The surrounding controller still enforces tool contracts, scope, budgets, and termination.

Calling something an agent does not establish reasoning quality, reliable execution, or broader authorization. Those require separate implementation and evaluation.

Build the mechanism

Narrow execution versus arbitrary programs

Our arithmetic tool parses a restricted expression tree. It permits a small operator set, rejects names/function calls, and caps size and numeric magnitude.

It never passes the expression to Python eval. A general code runner would require much stronger isolation and resource controls than this tutorial implements.

For future side effects, define authorization, idempotency, and retries carefully. Looking up a page and deploying a service have different consequences.

Build the mechanism

Testing capability and behavior separately

First test a deterministic planner through the controller. This checks validation and execution without depending on model output quality.

Then connect a real model planner and preserve malformed proposals and wrong choices as results. Controller acceptance is not the same as task success.

Compare with a fixed workflow under the same task set, available tools, and stated resource budget. An agent can remain an experimental branch if it adds no measured value.

Build the mechanism

Worked practice and a readiness check

Write the ticket tool contract, a valid call, an unknown-tool call, an extra-argument call, and a division-by-zero case. Predict the outcome of each before running it.

Explain a task where a fixed workflow is enough and another where an observation changes the next needed action.

You are ready when a model proposal, an authorized tool execution, an observation, and a final task result are distinct steps in your diagram.

Optional deeper study

Further study 21 Intuition

A model can propose calling a calculator, looking up a document, or inspecting a configuration. It does not gain authority merely by naming a function. A tool interface specifies which operations exist, which arguments are valid, and how results are returned. Application code enforces those rules.

Define a tool by name, input schema, output schema, authorization requirements, failure states and side effects. Separate read-only tools from actions that change external state. For this course, executable tools are a bounded arithmetic calculator and a fixed configuration validator. Neither exposes arbitrary Python evaluation, shell commands, network requests or file writes.

Optional deeper study

Further study 21 Validation layers

Parse the model response; validate its shape; check the tool name; validate argument keys/types/ranges; enforce authorization; execute with time/resource limits; normalize the observation; log the outcome. Never use eval on model-generated expressions. The bundled calculator parses an arithmetic AST, accepts a narrow operator set and caps length, tree size and numerical magnitude. These checks are instructional, not a general sandbox for arbitrary code.

Optional deeper study

Further study 21 Worked contract

validate_config accepts exactly timeout_ms as an integer in a documented range and retries as an integer in a documented range. An input containing an extra command field is rejected. An integer field should not silently accept Python's boolean subtype. The observation returns valid plus explicit errors; it does not return an unstructured exception traceback to the model.

Idempotency matters for side effects. Retrying a document lookup is usually harmless; retrying a deployment may create multiple releases. A real side-effecting tool needs an idempotency key, authorization and explicit retry semantics. We study these contracts without exposing deployment tools in the starter.

Optional deeper study

Further study 21 Experiment

notebook 27 exercises valid calls, unknown tools, missing arguments, oversized expressions, division by zero, extra fields and invalid value ranges. Predict whether each should be rejected before execution or reported as a tool failure. Build a small table of observable outcomes and expected traces.

The documentation assistant's useful executable behavior is narrow: calculate a retry delay from retrieved rules or validate a proposed configuration against the selected version. Generic shell access would expand risk and evaluation scope far beyond the task. Add capabilities only when an actual user task requires them.

Exit criterion: draw the boundary between a model's proposed call and authorized execution, and implement validation outside the prompt. Reading: R11 actions/observations; R03 agent/context topic. Tutorial: 27.
