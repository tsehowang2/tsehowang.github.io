harness

A harness is the application code around a model: it prepares inputs, validates and runs actions, tracks state and budgets, and records outcomes.

The controller makes the agent a runnable system

Imagine supervising a school trip. A list of possible tasks is not enough; someone must track what has happened and decide when to stop. An agent execution harness serves that coordination role in code.

Its state can contain the question, allowed version, observations, evidence IDs, step count, and status. The model proposes an action; the harness validates and executes it.

An evaluation harness has a different role: load tasks, run a specified system, check outcomes, and collect metrics. Both need versioned configuration, but they are not interchangeable.

A complete small loop

Initialize state. Ask the planner for a typed proposal. If it is a final answer, validate the response contract and stop. If it is a tool action, validate name, schema, scope, and bounds before executing.

Record the normalized observation, update state, and repeat within the budget. Terminate explicitly on invalid proposals, failures, exhaustion, timeout, or cancellation under the implemented policy.

Every path should leave a trace. An exception or repeated tool request should not silently turn into an invented successful answer.

A three proposal trace

Proposal one retrieves the retry rule. Proposal two calculates the cumulative delay. Proposal three returns the result with observed source IDs.

If instead the planner keeps requesting another calculation, a three-proposal budget eventually returns budget_exhausted. The controller does not keep going simply because the model asks politely.

Checking a citation ID against previously retrieved evidence establishes a structural boundary. Whether that passage supports the final claim remains an evaluation question.

Time and resource limits

A step cap bounds loop iterations but cannot interrupt a blocking network call. Checking elapsed time after a call returns does not impose a real call deadline.

Use client timeouts and cancellation for appropriate dependencies, and process/container controls for execution that needs isolation. Bound tool output and model context as well.

The synchronous reference controller demonstrates step limits and narrow arithmetic safety. It does not claim to be a complete arbitrary-code sandbox.

MCP connects the application to a tool provider

MCP means Model Context Protocol. Think about the calculator you already used: the model proposes a calculation, while application code checks the proposal and runs an allowed function. MCP gives an application a standard way to discover and call capabilities supplied by another program. It does not change the arithmetic or the need to validate a request [ Model Context Protocol architecture (R29) ].

Role Meaning in our example
Host The documentation-assistant application that manages the model, user interaction, and tool policy.
Client The component in the host that communicates with one MCP server.
Server The program that exposes the calculator and handles its requests; it may run locally or remotely.

After the connection is set up, the client can request tools/list. The server describes the available tools, including their names and input schemas. The host decides which tools to make available to the model. For the question “A bus ticket costs 4 dollars. What do three tickets cost?”, the model might propose the existing calculator with expression “3*4”.

The host checks the proposal and sends the permitted request through its MCP client using tools/call. The server checks the request, performs the allowed calculation, and returns the result 12. The host records the observation and can give it to the model to form the final answer. The model proposal and the protocol request are separate representations; application code connects them [ Model Context Protocol tools (R30) ].

MCP also defines resources for contextual data, such as a handbook passage, and prompts for reusable message templates. The distinction is simple here: a tool performs a specified operation, a resource supplies context, and a prompt supplies a reusable interaction template. The application still chooses how to use them.

Compare this with our direct function call. The direct version calls the calculator in application code. The MCP version adds a standard client/server interface for discovery and execution. The harness still controls state, allowed actions, and stopping. Exposing a tool through MCP does not automatically make its arguments valid or its use authorized.

Check your understanding: point to the host, client, server, model proposal, tool result, and harness in this example. A correct explanation of this boundary is enough for this course; you do not need to deploy an MCP server.

Planning methods

ReAct-style interaction alternates actions and observations. Plan-and-execute creates a proposed plan and then performs or revises it. Routing chooses a specialized workflow.

These patterns can be implemented with different libraries, but the same questions apply: what state is authoritative, what actions are permitted, what observation changes the plan, and what terminates execution?

Multiple agents add coordination, duplicated context, cost, and new failure modes. They are an optional advanced direction rather than a prerequisite for this single-controller project.

Memory has several meanings

Current chat history, structured task state, retrieved documents, and persistent user memory have different lifetimes and trust properties.

A summary can compress text but omit a condition. If a user switches from version 1 to a comparison with version 2, preserve that intent explicitly instead of trusting a summary saying “user uses version 1.”

Authorization must come from authenticated application state, not model-written memory. Keep critical constraints and source provenance in structured fields.

Task evaluation inspects traces

A final sentence can look correct while hiding a forbidden action or missed required calculation. Measure task success, call validity, forbidden calls, failures, budgets, latency, and total model work.

An agent that never uses a required tool should not receive credit for an empty “valid-call” denominator. Define success predicates and audit traces.

Retries need bounded, operation-specific behavior. Invalid arguments and non-idempotent side effects cannot be retried blindly as though they were transient read timeouts.

Worked practice and a readiness check

Use the visual harness for success, unknown tool, wrong version, and endless planner scenarios. Then run an actual model planner and compare with the deterministic workflow.

Prepare at least 20 independently checked tasks and preserve both successful and failed traces. Explain one useful adaptive choice and one unnecessary action.

You are ready when your agent is a bounded state machine with observable behavior rather than an unexamined prompt-to-framework call.

Reference details and checks

Review A: Intuition

A workflow has a largely predetermined control path. An agent lets model outputs influence which action happens next. Both need orchestration code. Agentic behavior is useful when tasks require adapting to observations; it can be unnecessary overhead for a fixed lookup.

The word harness has two relevant meanings. An agent execution harness manages state, model calls, tools, budgets, observation limits, cancellation and termination. An evaluation harness loads tasks, runs a specified system, records results and computes metrics. They may integrate, but they have different responsibilities. Naming both prevents the vague claim “we have a harness” from hiding missing controls.

Review A: State and transitions

Represent state explicitly: question, allowed version, evidence IDs, observations, step count, token/cost budget, status and error. A planner proposes either a tool action or a final response. A controller validates it, executes allowed actions and updates state. Termination reasons include success, invalid proposal, tool failure, step exhaustion, timeout and cancellation. Every path must be observable.

Review A: Worked trace

Step 1 retrieves retry rules. Step 2 calls a calculator with a bounded expression. Step 3 answers with the numerical result and source IDs. A repeated failed calculator call should not run forever. With a maximum of three planner steps, a proposal on the final step that still requires another observation should end with an explicit budget-exhausted status rather than a fabricated final answer.

Wall-clock limits require real enforcement. Checking elapsed time only after a blocking call returns cannot interrupt that call. Use client timeouts for network tools and process/container limits for untrusted execution. Our synchronous starter enforces step limits and arithmetic bounds; its deployment extension requires per-call timeout/cancellation implementations.

Review A: Experiment

Tutorial 27: Tools functions workflows and agents runs a deterministic planner through the controller to test the execution contract. This is a controller fixture, not evidence of LLM planning. Tutorial 28: Harnesses planning memory and bounded execution connects a real model planner. Inject a planner that never stops, one that returns malformed JSON and one that invents a tool. Verify explicit terminal states and a finite number of tool calls.

For each trace, ask whether the information shown to the model is necessary. Large tool outputs can overflow context or carry adversarial instructions. Bound and label observations, preserve authoritative metadata separately, and avoid treating tool text as new policy.

Exit criterion: implement a bounded state machine and distinguish execution from evaluation harnesses. Reading: Yao et al. ReAct (R11) ; Hung-yi Lee Introduction to GenAI and ML 2025 (R03) context engineering topic. Tutorial: 28.

Review B: Intuition

An agent's “memory” can mean its current prompt, a task scratch state, retrieved documents, or a persistent store of previous interactions. These have different retention and trust properties. More remembered text is not automatically more useful context.

Maintain a typed task state for facts such as requested version, selected source IDs and tool outcomes. Summaries can compress long histories, but they can omit an exception or turn an uncertain observation into a confident assertion. Preserve critical constraints in structured fields and retain source provenance.

Review B: Planning patterns

ReAct-style systems interleave action selection and observations. Plan-and-execute generates a plan and then performs it, potentially revising it when observations disagree. Routing chooses a specialized workflow. Multi-agent systems distribute roles but add coordination, duplicated context, cost and evaluation complexity. A single bounded controller is the core path here; multi-agent implementation is not required.

A fixed workflow for versioned lookup may be retrieve, pack, answer and validate. A troubleshooting task may benefit from conditional actions: inspect version, retrieve a rule, validate a config, then explain the first violated requirement. The latter supplies a concrete reason for adaptive planning.

Review B: Worked memory failure

A user first asks about v1, then says “now compare that with v2.” A summary storing only “user uses v1” can cause the next retrieval to filter out v2. Keep the task's allowed versions and comparison intent explicit. Authorization should come from authenticated application state, never from conversational memory or model-generated summaries.

Review B: Experiment

Tutorial 28: Harnesses planning memory and bounded execution converts a small model's JSON proposal into a controller action. Compare it with a fixed workflow on the same set of lookups, calculations and troubleshooting tasks. Count invalid proposals, unnecessary tool calls, missed required actions, completion, latency and total model tokens. A small model may fail often; use those traces to decide where a deterministic route is preferable.

Test a long irrelevant observation and a misleading instruction embedded in a retrieved page. Verify that policy fields stay outside the model's authority. A failed model proposal must produce a controlled result, not fall back to executing guessed arguments.

Exit criterion: justify adaptive planning for a specific task and identify which state belongs in structured memory. Reading: Yao et al. ReAct (R11) ; Hung-yi Lee Introduction to GenAI and ML 2025 (R03) context engineering. Tutorial: 28.

Review C: Intuition

A convincing final sentence can hide a failed or forbidden action. Agent evaluation must inspect the environment and trace, not merely score final text. For read-only tools, correctness includes choosing the right evidence and calculation. For side effects in a future extension, it also includes the final state and the absence of unintended changes.

Define tasks with initial state, allowed actions, expected results and success predicates. Compare a model-only answer, a fixed tool workflow and the adaptive controller. Keep the tool affordances and budgets comparable. An agent given ten attempts should not be compared with a workflow allowed only one without reporting that difference.

Review C: Metrics and recovery

Task success, valid-call rate, forbidden-action rate, tool failures, step count, budget exhaustion and cost are complementary. A system that never calls a tool can have a perfect valid-call rate on an empty denominator; report how often it used tools and whether tasks required them. Failure should be typed so analysis can separate planning, validation, execution and answer errors.

Retries must be bounded and appropriate. A transient read timeout may merit one backoff/retry. Repeating invalid arguments does not repair the schema. A non-idempotent side effect cannot be retried blindly. A circuit breaker limits repeated calls to a failing dependency; it does not replace correct per-request handling.

Review C: Worked audit

An agent completes 18/20 tasks, but one successful task includes an unauthorized call that happened to return harmless data. Under a zero-forbidden-action release gate, it fails. Another system completes 17/20 with no violations and clearly reports three controlled failures. Depending on requirements, the latter may be the deployable candidate. State the gate before evaluating.

Review C: Experiment

Create at least 20 tool tasks with deterministic checkers, including division by zero, unknown tool, wrong version, invalid config, misleading documentation and a forced step-limit failure. Run Tutorial 28: Harnesses planning memory and bounded execution , preserve full action/observation traces, and hand-audit a sample. Report failure counts even when the final answer looks reasonable.

For open-ended troubleshooting, use a rubric plus manual review rather than pretending one exact string captures success. Your project report should include one case where the agent adds value and one where the fixed workflow is simpler and equally effective. If the agent never improves your tasks, it can remain an evaluated experimental branch rather than the default product.

Exit criterion: defend an agent release decision using trace-level evidence and recovery behavior. Reading: Stanford CS329S Machine Learning Systems Design (R02) stakeholder requirements; Yao et al. ReAct (R11) task/action evaluation. Tutorial: 28.
