CUDA kernels and profiling

Tutorial 23Test your understanding
Lecture slides · Week 23

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

One operation many independent elements

Take two vectors of 257 numbers and add corresponding elements. A CPU loop is easy to understand: for each index i, compute c[i]=a[i]+b[i].

A CUDA kernel can assign this elementwise work across threads on a GPU. The mathematical result stays the same. What changes is how the program assigns work, accesses memory, and measures execution.

We begin with vector addition rather than a custom attention kernel because correctness and indexing should be transparent before optimization becomes complicated.

Start with an example

Threads blocks and an index

A one-dimensional kernel can compute i=blockIdx.x×blockDim.x+threadIdx.x. If a block has 256 threads, two blocks provide 512 thread indices for a length-257 vector.

Threads with i≥257 must not access the arrays. The bounds check is part of correctness, not a disposable optimization detail.

Blocks can execute independently. Do not assume an ordinary kernel has a general synchronization barrier across the whole grid.

Build the mechanism

Host and device responsibilities

The CPU host allocates or prepares inputs, manages device memory, transfers values where required, launches the kernel, and retrieves results.

GPU device code performs the per-thread operation. A kernel launch does not mean every result is immediately available to the CPU; execution can be asynchronous.

Follow the sequence in the provided CUDA C++ example and identify which statements belong to allocation, transfer, launch, synchronization, timing, and cleanup.

Build the mechanism

Memory access and arithmetic intensity

For float32 vector addition, two input reads and one output write move roughly twelve bytes per addition, ignoring caching and other effects. That is low arithmetic intensity.

Adjacent threads reading adjacent elements can allow efficient memory transactions. Scattered accesses and repeated unnecessary transfers can hurt performance.

Matrix multiplication can reuse values in tiles and reach a different balance between arithmetic and movement. Kernel optimization requires understanding that reuse and the device rather than assuming more threads always means faster work.

Build the mechanism

Timing an asynchronous device

Timing only a launch with a CPU clock may mostly measure dispatch. Use CUDA events or synchronization around the interval being measured.

Warm up, repeat measurements, and report a median and spread. State whether transfers, allocation, compilation, and first-run effects are included.

Kernel-only time and end-to-end application time answer different questions. Keep both when diagnosing whether an optimization matters to the actual workload.

Build the mechanism

Amdahl reasoning for a practical optimization

Suppose the full task takes 20 ms, including a 3 ms kernel. Making that kernel twice as fast reduces total time to 18.5 ms, a speedup of about 1.081.

The arithmetic explains why a dramatic kernel speedup can yield a modest user-visible improvement. Optimize the components that dominate the measured task.

A wrong result is not a speedup. Validate against a CPU reference with appropriate tolerances before reporting performance.

Build the mechanism

Profiling the transformer operations

Use a profiler to inspect operator times, shapes, memory, and CPU/GPU activity. Start with a short reproducible workload and save the trace.

FlashAttention is an example of redesigning attention computation to reduce memory traffic while preserving its mathematical operation subject to numerical behavior. It is not a different language-model objective.

Custom kernels and distributed training are deeper areas. Our required exercise establishes introductory CUDA indexing, correctness, synchronized measurement, and bottleneck diagnosis.

Build the mechanism

Worked practice and a readiness check

Run sizes 1,257, and a larger vector. Explain why the awkward size matters. Repeat with different block sizes while retaining bounds checks.

Profile a matrix multiplication or short model pass. Separate transfer and execution costs, and identify one bottleneck supported by the trace.

You are ready when your performance claim includes correct outputs, a timing boundary, device/software details, and a reproducible workload.

Optional deeper study

Further study 10 Intuition

PyTorch operations eventually execute kernels. A CUDA kernel specifies work for many threads. Writing one small kernel makes launch overhead, indexing, memory access and synchronization concrete, even if most application work should continue using optimized libraries.

For a one-dimensional array, thread index i = blockIdx.x * blockDim.x + threadIdx.x. A vector-add kernel computes c[i]=a[i]+b[i] when i<n. The bounds check matters when n is not divisible by the block size. Blocks are scheduled independently; code must not assume a general grid-wide barrier inside an ordinary kernel.

Optional deeper study

Further study 10 Memory and performance

Adjacent threads reading adjacent elements often produce more efficient memory transactions than scattered accesses. Shared memory can reuse data within a block, but reuse must justify its loading and synchronization overhead. A barrier must be reached consistently by participating threads. Occupancy is one diagnostic, not an objective that guarantees maximum speed.

Arithmetic intensity is approximate operations divided by bytes moved. Vector addition performs roughly one addition for two input reads and one output write: about 1/12 operations per byte for float32, ignoring caching. This is low intensity, so increasing theoretical arithmetic throughput may help little compared with memory bandwidth. A matrix multiplication can reuse tiles and attain much higher intensity.

Optional deeper study

Further study 10 Timing worked example

GPU work is asynchronous relative to the host. Timing a launch without synchronizing may mostly measure dispatch. Use CUDA events or synchronization around the defined measurement interval. Warm up first, repeat the operation, and report a median and spread. Include data transfers only if your stated question is end-to-end latency; separately report kernel-only time when studying the device operation.

Suppose end-to-end time is 20 ms, of which 3 ms is the kernel. Making the kernel twice as fast yields 18.5 ms total, a speedup of only 1.081. This is Amdahl-style reasoning: optimize what dominates the real task.
