Agents and harnesses

Explore the mechanism

The agent and its controller

Try valid actions, unknown tools, wrong scope and an unending planner.

Enable JavaScript to use this illustration. The lecture notes below explain the same mechanism.

Intuition

A workflow has a largely predetermined control path. An agent lets model outputs influence which action happens next. Both need orchestration code. Agentic behavior is useful when tasks require adapting to observations; it can be unnecessary overhead for a fixed lookup.

The word harness has two relevant meanings. An agent execution harness manages state, model calls, tools, budgets, observation limits, cancellation and termination. An evaluation harness loads tasks, runs a specified system, records results and computes metrics. They may integrate, but they have different responsibilities. Naming both prevents the vague claim “we have a harness” from hiding missing controls.

State and transitions

Represent state explicitly: question, allowed version, evidence IDs, observations, step count, token/cost budget, status and error. A planner proposes either a tool action or a final response. A controller validates it, executes allowed actions and updates state. Termination reasons include success, invalid proposal, tool failure, step exhaustion, timeout and cancellation. Every path must be observable.

Worked trace

Step 1 retrieves retry rules. Step 2 calls a calculator with a bounded expression. Step 3 answers with the numerical result and source IDs. A repeated failed calculator call should not run forever. With a maximum of three planner steps, a proposal on the final step that still requires another observation should end with an explicit budget-exhausted status rather than a fabricated final answer.

Wall-clock limits require real enforcement. Checking elapsed time only after a blocking call returns cannot interrupt that call. Use client timeouts for network tools and process/container limits for untrusted execution. Our synchronous starter enforces step limits and arithmetic bounds; its deployment extension requires per-call timeout/cancellation implementations.

Experiment

Notebook 11 runs a deterministic planner through the controller to test the execution contract. This is a controller fixture, not evidence of LLM planning. Notebook 12 connects a real model planner. Inject a planner that never stops, one that returns malformed JSON and one that invents a tool. Verify explicit terminal states and a finite number of tool calls.

For each trace, ask whether the information shown to the model is necessary. Large tool outputs can overflow context or carry adversarial instructions. Bound and label observations, preserve authoritative metadata separately, and avoid treating tool text as new policy.

Exit criterion: implement a bounded state machine and distinguish execution from evaluation harnesses. Reading: R11; R03 context engineering topic. Lab: 11.
