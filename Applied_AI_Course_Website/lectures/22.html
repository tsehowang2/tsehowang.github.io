CPU GPU memory and model resource accounting

Tutorial 22Test your understanding
Lecture slides · Week 22

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

Numerical work happens on physical hardware

A transformer contains matrix multiplications, elementwise operations, and memory access. A CPU can run a small model. A GPU can execute many suitable operations in parallel, but performance also depends on data movement and memory capacity.

Separate host RAM from GPU VRAM. A model downloaded to disk does not automatically fit in either. A tensor copied between CPU and GPU incurs movement and coordination.

We study the hardware now that you can identify the tensors it stores and operations it executes.

Start with an example

Parameters are only the first memory item

If a model has P parameters stored with b bytes each, weight memory is P×b. For 500 million parameters at two bytes, that is one billion bytes, about 0.93 GiB.

During training, gradients, optimizer moments, optional master weights, activations, and temporary buffers add memory. During generation, a KV cache can be large.

An inference weight estimate therefore does not answer whether the model can train or handle a long batched context.

Build the mechanism

A worked training state estimate

An illustrative mixed-precision Adam arrangement uses 2 bytes of weights, 2 of gradients, 4 of master weights, and 8 for two optimizer moments per parameter. That totals 16 bytes before activations and overhead.

At 500 million parameters, counted state is 8 billion bytes, about 7.45 GiB. Different implementations and precision choices change the accounting.

The interactive worksheet explicitly reports partial estimates. Being below a VRAM line in that worksheet is not proof that a real runtime will fit.

Build the mechanism

A KV cache calculation

Approximate cache bytes equal 2×layers×batch×tokens×KVheads×head_dimension×bytes. The factor two accounts for keys and values.

With 24 layers, batch 1, 2048 tokens, eight KV heads, dimension 64, and two-byte values, the result is 100663296 bytes, or 96 MiB.

Longer context and larger batch multiply this quantity. Grouped-query attention uses fewer KV heads than query heads; inspect the architecture rather than substituting the query-head count automatically.

Build the mechanism

Memory hierarchy and movement

GPU execution uses registers, shared memory within blocks, caches, and device DRAM under hardware-specific arrangements. Large tensors live in device memory; moving and re-reading them can dominate an operation.

A high advertised arithmetic rate does not guarantee a fast application. A low-arithmetic-intensity operation can spend much of its time moving values.

Next week's kernel makes this visible with vector addition. The operation is simple enough that indexing and transfer boundaries can be checked independently.

Build the mechanism

Smaller microbatches and checkpointing

Gradient accumulation lets several small microbatches contribute to one effective update. It can reduce the batch portion of activation memory, but persistent model/optimizer state remains.

If one sequence already causes OOM, accumulation alone cannot shrink that sequence's footprint. Shorter context, activation checkpointing, a smaller model, or state sharding may address different components.

Activation checkpointing saves some intermediate storage by recomputing work during backward. The tradeoff is extra computation, not free memory removal.

Build the mechanism

Choosing precision and measuring reality

Float32, float16, bfloat16, and quantized representations have different numerical ranges, memory costs, and support. Do not assume your GTX 1650 Super supports every optimized dtype or kernel.

Use actual device properties and compatible software. A free Colab session may offer a different GPU or no GPU, so save checkpoints and measured metadata.

Record allocated and peak memory under a defined workload. Allocator reservation and warmup can make a simplistic reading misleading.

Build the mechanism

Worked practice and a readiness check

Calculate weight-only memory for 300 million two-byte parameters and compare with a 16-byte training-state estimate. List omitted components in both.

Change context length from 2048 to 4096 in the cache formula and explain the doubling. Then identify a memory issue that accumulation can help and one it cannot.

You are ready when you can link resource costs to particular tensors and distinguish an estimate, an actual measurement, and a hardware capability assumption.

Optional deeper study

Further study 9 Intuition

A GPU accelerates many similar arithmetic operations, but a model must also move data and fit its working state into memory. “More FLOPs” alone does not predict whether your experiment will run or be fast. Distinguish CPU RAM, GPU VRAM, device memory bandwidth, host-to-device transfers and compute throughput.

The CPU schedules work and launches kernels. GPU execution groups threads across streaming multiprocessors. Registers are close to individual execution contexts, shared memory is visible within a block, caches serve broader access, and device DRAM stores large tensors. A tensor moving repeatedly between CPU and GPU can dominate a short computation even if the arithmetic is fast.

Optional deeper study

Further study 9 Training versus inference

Parameter storage is parameter_count * bytes_per_parameter. Training may additionally store gradients, optimizer moments, master weights and activations. For an illustrative mixed-precision Adam configuration, 2 bytes of model weights + 2 bytes of gradients + 4 bytes of master weights + 8 bytes of two moments gives 16 bytes per parameter before activations and overhead. This is an example configuration, not a universal rule; frameworks and precision choices differ.

For 500 million parameters, that illustrative state is 8 GB decimal. A 2-byte inference weight copy alone is 1 GB decimal. A model that fits for inference can therefore fail in training. LoRA reduces trainable parameter state, but activations and frozen base weights still occupy memory.

Optional deeper study

Further study 9 KV cache worked example

During autoregressive inference, cached keys and values avoid recomputing earlier projections. An approximate KV-cache size is 2 * layers * batch * tokens * kv_heads * head_dim * bytes. For 24 layers, batch 1, 2,048 tokens, 8 KV heads, dimension 64 and 2-byte values, the cache is 100,663,296 bytes, or 96 MiB. Increasing batch or context multiplies this. Grouped-query attention can use fewer KV heads than query heads.

The original full attention score tensor also scales quadratically in sequence length when explicitly materialized. Memory-efficient attention implementations avoid storing all those intermediate scores in device DRAM, while retaining the operation's mathematical meaning subject to numerical precision differences.

Optional deeper study

Further study 9 Experiment

notebook 23 measures the device rather than assuming its capabilities. Calculate weight, optimizer and KV-cache estimates on paper, then compare allocated and peak memory. Account for warmup and allocator reservations. When an out-of-memory error occurs, reduce sequence length and microbatch before reaching for a different framework. Gradient accumulation changes effective batch but does not shrink the memory required by a single microbatch.

Exit criterion: explain why a model fits inference but not training, and estimate a context-dependent cache. Reading: R01 resource-accounting topic; R16 memory hierarchy. Tutorial: 22.
