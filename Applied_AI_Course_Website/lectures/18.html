A vector database from a list of vectors

Tutorial 18Test your understanding
Lecture slides · Week 18

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

Persistence becomes useful when the list changes

Last week we could keep three handbook vectors in memory and compare them directly. Now imagine thousands of passages, updates each term, and questions arriving after restarting the program.

A vector database helps maintain vectors and associated information across those operations. Begin with a point containing an ID, vector, source text reference, and metadata. The database is responsible for storing and searching those points under its supported behavior.

The embedding model creates the vector. The similarity metric defines a comparison. The index organizes search. The database adds management and operational capabilities. These are related components with different jobs.

Start with an example

A record you can inspect

Represent H2 as ID=bus-2026, vector=[...], version=2026, source=handbook transport section, and content hash. A question about 2025 should not silently use 2026 rules if those rules changed.

Metadata filters limit eligible passages. Text, vector, and version must remain associated through updates. A correct nearest-neighbor algorithm cannot repair a record whose version was mislabeled during ingestion.

Stable IDs help update an existing passage rather than accumulating duplicates. The exact update semantics depend on the database API and need a save/reload test.

Build the mechanism

Exact search provides a reference

Exact search compares the query against every eligible stored vector and selects the best under the metric. It can be perfectly adequate for a small collection.

As the collection grows, approximate nearest-neighbor methods can trade additional structure and resources for reduced search work. Approximation concerns the chosen vector metric; even exact vector neighbors can be semantically irrelevant if the embeddings are poor.

Keep those two error sources separate: approximation may miss an exact neighbor, while representation quality may make the exact neighbor unhelpful for the question.

Build the mechanism

A graph intuition for HNSW

An approximate graph index connects points so search can navigate through promising neighbors instead of checking every point. HNSW uses a hierarchy of navigable graph layers.

The intuition is navigating a map using increasingly local connections, but the real structure consists of vector-space points and algorithmic rules. Search breadth and construction settings affect recall, latency, and storage.

Measure approximate results against exact results on the same query vectors and metadata constraints. Nine teaching points in local mode cannot establish production HNSW performance.

Build the mechanism

Filtering before or after candidate selection

Suppose the first three unfiltered results all belong to 2026, while the question asks about 2025. Retrieving three and then deleting the wrong-year points can leave nothing even though relevant 2025 evidence exists lower in the unfiltered ranking.

Apply required constraints through the search mechanism and evaluate its filtered behavior. In a private system, authorization must be enforced by application/database controls rather than model-generated advice.

For the public teaching corpus, version filtering is a scope constraint. It should not be described as complete authentication or multi-tenant security.

Build the mechanism

Storage arithmetic and compatibility

One million 384-dimensional float32 vectors contain 1,536,000,000 raw vector bytes. That excludes graph links, IDs, payloads, text, replicas, and allocation overhead.

Two embedding models with dimension 384 do not necessarily share a coordinate system. Changing the model normally requires re-embedding and a compatible index, even though the database accepts the same vector length.

Record the actual model/tokenizer revision and source manifest. Dimension checking catches one class of mismatch; identity checking catches another.

Build the mechanism

Updates deletion and migration

If the handbook changes a bus departure time, update the source record and dependent vector/index state. If a passage is removed, ensure its index entries and any cached answers are addressed.

For a model migration, build a separate compatible collection, validate point counts and IDs, benchmark retrieval, then switch the active collection only after the chosen gates pass. Retain the earlier collection for a coherent rollback.

This is where data-engineering discipline becomes directly useful. The learned vector representation still requires lineage, schema checks, and a lifecycle.

Build the mechanism

Worked practice and a readiness check

Persist a local collection, close it, reopen it, and repeat a filtered query. Update one point with the same ID and verify the new content. Delete another and verify it is absent.

Explain whether a failed query comes from ingestion, a filter, the embedding representation, or approximation. Design one test that separates two of those causes.

You are ready when “vector DB” means a maintained collection and search service with explicit compatibility and update behavior, not a synonym for the embedding model.

Further study 12 Intuition

A list of vectors and cosine scores demonstrates semantic search. A vector database adds persistent collections, metadata, updates, filtering and operational behavior. These matter because documentation changes while users keep querying. The index is an artifact with a lifecycle, not a one-time preprocessing step.

Store each point with a stable ID, embedding, source reference, version, content hash and payload. Track the embedding model and tokenizer revision in the collection manifest. Two models can both output 384 numbers yet produce incompatible geometries. A model migration normally requires re-embedding and creating or rebuilding an index; do not mix vectors because their dimensions match.

Further study 12 Exact and approximate search

Exact nearest-neighbor search evaluates all candidates and gives a useful reference. Approximate nearest-neighbor search trades work and storage for retrieval quality. HNSW builds a navigable graph; search breadth affects speed and recall. Index settings must be evaluated against exact results under the real metadata filters, not just against an unfiltered random benchmark.

Filtered search can behave differently when only a small fraction of documents match. Applying a version filter after retrieving a short top-k list may leave no valid candidates even when relevant documents exist. Apply constraints through the retrieval mechanism and measure the result. Security-related authorization filters must not be delegated to the language model.

Optional deeper study

Further study 12 Worked migration

Suppose index A contains model M1 vectors and 10,000 source chunks. Build index B with M2 and the same source manifest. Check row counts, missing IDs, embedding dimensions and a development retrieval benchmark. Route a limited evaluation workload to B, then switch the active index only when gates pass. Retain A for rollback. If documents changed too, record that as a separate experimental variable.

Deletion matters. Removing a document from object storage does not automatically remove its chunks, cached answers or replicated index entries. Define a tombstone/update policy and a completion check.

Optional deeper study

Further study 12 Experiment

notebook 18 creates a local Qdrant collection, upserts vectors, filters by version, persists and reopens it, and queries again. Inspect payloads directly. Add an update with the same ID, then delete a point and verify it no longer appears. Local mode teaches the client and lifecycle; it does not establish distributed durability or production throughput.

Exit criterion: distinguish an embedding model, a vector similarity function, an ANN index and the database operating it. Reading: R08; optional R24. Tutorial: 18.
