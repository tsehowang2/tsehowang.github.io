A final explanation begins with the basics

Explain “I go to school by bus” from tokenization to logits, then explain how a documentation question adds external evidence and controlled tools.

The ability to connect those levels is the central outcome. Recognizing framework names without understanding their model and evidence boundaries is insufficient.

Return to the first lecture's questions: What input was available? What output was expected? What computation produced it? How was it checked?

A transformer review

IDs select embeddings. Position information enters. Attention projections form comparisons and value mixtures under visibility constraints. Residuals, normalization, and MLPs construct new contextual representations.

The vocabulary head produces logits. Training compares with shifted targets and propagates gradients. Generation chooses a token, appends it, and repeats with appropriate cache reuse.

Explain one mask bug and one label-shift bug, including why either can produce misleading loss or behavior.

An application review

Sentence embeddings support a retrieval comparison under a trained geometry. A vector database maintains compatible points, metadata, and updates.

RAG selects evidence and conditions generation, while answer checks distinguish support, completeness, absence, and scope. Fine-tuning changes learned behavior under reviewed targets and a measured objective.

Tools expose narrow capabilities. The execution harness controls actions and budgets; the evaluation harness checks tasks and outcomes.

An operations review

A manifest identifies model, prompt, tokenizer, index, source, adapter, tool, environment, and evaluation dependencies. A service enforces contracts and resource behavior.

Monitoring and traces support diagnosis. Authorization belongs outside untrusted model/document text. A release decision uses declared gates and a coherent rollback plan.

Distinguish an actual public deployment, a local deployment, and a proposed architecture. All can be useful evidence, but they are different claims.

What to show in the defense

Present one clear problem, the task set, a baseline, one controlled improvement, raw examples, limitations, and a reproducible run.

For “Why an agent?”, show a task requiring an adaptive decision and its comparison with a fixed workflow. For “Why fine-tune?”, show the repeated error, training intervention, and independent outcome.

If the experiment failed to improve the baseline, explain the finding and release the better system. Do not rewrite a negative result into an invented success.

The examination and correction process

Take the second semester exam under the stated conditions. Use the marking guide only after an unaided attempt, then explain each error in your own words.

An error about terminology can be corrected by a precise definition and example. An error about a mechanism needs a numerical trace or property test. An error about evaluation needs a better task or denominator.

This correction process turns a grade into a concrete next learning action.

A focused next step

Choose a next experiment based on observed weakness: retrieval misses, long-context reasoning, training-data quality, tool planning, multimodal extraction, or serving efficiency.

Avoid expanding all directions at once. A narrowly measured improvement can provide stronger delivery evidence than another untested broad prototype.

Keep reading primary papers and official documentation with a mechanism, shape trace, and testable question in mind. You now have enough structure to make the compact explanations more useful.

Worked practice and final reflection

Record three decisions supported by evidence, two unresolved limitations, and one focused next experiment. Include source/model provenance and assistance disclosure.

Describe the work as an independent personal project with the actual dataset, model, implementation, and measurements you produced. Workplace or paid-client experience requires those things to have happened.

You have completed the course when another person can run the release, inspect the evaluation, and hear a clear explanation from ordinary examples through the harder mechanisms.

Reference details and checks

Review A: Intuition

Credible delivery evidence consists of an artifact someone can run, evaluations someone can inspect, and reasoning you can defend. A polished demo becomes stronger when you also show failure behavior, release constraints and the limits of your claims.

Your final project is a version-aware documentation assistant with semantic retrieval, source citations and narrowly executable tools. It includes a compared lexical baseline, a bounded workflow or agent controller, a measured adaptation experiment, an API and operations evidence. The default deployed branch may use the base model if fine-tuning did not help; the measured negative experiment still demonstrates sound engineering.

Review A: Final audit

Start from a clean directory and follow your README. Verify source ingestion, artifact compatibility, index loading, inference or explicitly documented offline fallback, test execution and example requests. Record environment details and dependency downloads. Another reader should be able to distinguish what runs without internet from what requires model downloads or GPU access.

Freeze raw final evaluation outputs before writing conclusions. Include task slices, paired comparisons where appropriate, quality and latency, tool safety, uncertainty and limitations. Label exploratory analyses that used the held-out results. Never turn hypothetical metrics in a template into claimed measurements.

Review A: Defense worked example

Question: “Why did you add an agent?” A defensible answer names a task requiring conditional inspection, compares with a fixed workflow and shows trace-level success/cost. “Agents are more advanced” does not justify the choice. Question: “Why fine-tune?” A defensible answer links a repeatable error pattern to a targeted objective and reports the controlled comparison, including regressions.

Review A: Submission

Present a five-minute demo: one supported lookup, a cross-version comparison, a tool task, an unsupported question and a controlled failure. Include your final report, reproducibility manifest, architecture description, evaluation harness, test data and licenses/provenance. Keep checkpoints or model-download instructions separate from source code where necessary. Follow the capstone rubric and record your own contributions and any assistance.

Take semester exam 2 for two hours and use the solution rubric afterward. Then write a one-page reflection: three decisions justified by evidence, two unresolved weaknesses and one focused next project. Describe this work in applications as a personal project with the actual model, dataset and results you produced. Paid-client, workplace or production experience requires those things to have happened.

Exit criterion: a fresh run succeeds, the release meets your stated gates, and you can explain every component and failure in the demo. Reading: revisit Stanford CS329S Machine Learning Systems Design (R02) system objectives. Tutorial: 32. Assessment: semester exam 2 and capstone defense.
