From a notebook to MLOps and inference serving

Lecture slides · Week 29

Learn one step at a time.

Start with an example

A saved model and a running service

A notebook runs when you execute its cells. A service accepts requests from callers, manages resources, and returns defined responses even when something fails.

For the documentation assistant, a request needs a question and scope; a response needs answer/status, citations, and release identity. The chosen model is one dependency inside this service.

Begin with a local loopback API. Public hosting introduces additional access, resource, and infrastructure requirements that should be implemented and described explicitly.

Start with an example

The artifacts that define a release

A release depends on sources, chunker, embedding model, index, generator, tokenizer, adapter if used, prompt, tool schemas, and environment.

A prompt change can alter behavior without changing weights. An embedding change normally requires compatible new vectors/index. A source deletion affects downstream evidence and possibly caches.

MLOps manages development, provenance, evaluation, and operation of model-dependent systems. LLMOps emphasizes the particular prompt, retrieval, and tool dependencies in this setting.

Build the mechanism

A run manifest

Record source hashes, model/tokenizer revisions, index identity, prompt hash, tool version, decoding settings, code/environment, seed where applicable, and raw outputs.

A manifest helps another person reproduce the evaluated configuration. A content hash identifies bytes but does not prove quality or permissions.

Do not put secret values in the manifest or source repository. Document required secret names and environment setup separately.

Build the mechanism

Request handling

Validate input size and schema, apply scope controls, run retrieval and generation under limits, validate the result, and return a controlled status.

Use bounded queues and appropriate dependency timeouts/cancellation. A health check should not require a full expensive model query, while readiness may need to confirm required artifacts are available.

The instructional API is a starting contract, not evidence of multi-tenant authentication or production capacity.

Build the mechanism

Prefill and decode

Prompt processing is often called prefill. Subsequent autoregressive steps decode new tokens while using cached state.

Time to first token includes queueing, retrieval, prompt work, and initial generation. End-to-end time continues until the response finishes. Inter-token timing describes subsequent output speed.

Throughput measures useful completed work per unit time. Improving throughput through batching can change latency and memory use, so define the workload before claiming a serving improvement.

Build the mechanism

A simple capacity consistency check

At an average arrival rate of two requests per second and average time in system of three seconds under a stable regime, Little's law suggests six requests in the system on average.

This does not determine a safe worker count or predict p95 latency. Variation, saturation, scheduling, batching, and failures still matter.

Use the arithmetic as a consistency check and then run a measured load experiment on representative input/output lengths.

Build the mechanism

Experiments and release dependencies

Tracking tools can save runs, parameters, metrics, and artifacts. A small structured JSON record is enough to learn the concepts before adopting a service.

Choose checks based on changed dependencies. A prompt edit needs behavioral evaluation; an embedding migration needs retrieval compatibility and downstream tests.

Keep the training and serving templates aligned. Evaluating one prompt/chunker and serving another creates a mismatch even when the source model is unchanged.

Build the mechanism

Worked practice and a readiness check

Run the local API, verify scoped citations, and record actual end-to-end timings. Then integrate the chosen real model and repeat with lengths, concurrency, warm/cold state, and failures stated.

Create a manifest and deliberately test a mismatch. Reproduce one evaluation from a clean directory.

You are ready when another person can identify the running release, invoke its contract, and distinguish observed performance from a proposed deployment plan.

Optional deeper study

Further study 25 Intuition

A model is only one artifact in an LLM application. The corpus, chunker, embedding model, vector index, generator, adapter, prompt, tool schemas and evaluation dataset evolve together. MLOps manages reproducible development and operation of model-dependent systems; LLMOps adds particular emphasis on these prompt, retrieval and tool dependencies.

Treat the pipeline as a dependency graph. A chunker change invalidates chunk IDs and embeddings. An embedding change invalidates vector compatibility. A prompt change can alter tool selection without changing weights. A tool schema change may break a saved planner prompt. Each release should identify the versions expected to work together.

Optional deeper study

Further study 25 Experiment records and registry

A run stores parameters, measured metrics and artifacts. An artifact registry associates immutable outputs with provenance and evaluation. MLflow is one implementation of these ideas [R20]; a small JSON-based record is sufficient to learn them. Store secrets outside configs and redact logged inputs where necessary.

Data lineage includes raw source hash, transformation version, time, license and resulting chunk IDs. A content hash detects changed bytes but does not prove semantic quality or authorization. A reproducibility manifest also needs environment and configuration. The phrase “same code” is insufficient when a remote model identifier silently resolves to a different revision.

Optional deeper study

Further study 25 Worked change-impact analysis

Changing a system prompt normally requires answer/agent regression tests but not re-embedding unchanged source chunks. Changing the embedding model requires an index rebuild and retrieval benchmark. Changing a document's access group requires updating authorization payloads and checking caches even if the text stays identical. Use the dependency graph to select checks rather than rerunning expensive training for every edit.

Further study 26 Intuition

An offline notebook processes one request when you press Run. A service handles concurrent requests, slow clients, cancellations, unavailable dependencies and bounded resources. Performance must be defined at the user's boundary as well as inside the model.

Time to first token includes queueing, retrieval, prompt processing and initial generation. Inter-token latency measures subsequent output speed. End-to-end latency includes the whole response. Throughput counts useful completed work per unit time. A fast single-request benchmark does not establish acceptable tail latency under load.

Optional deeper study

Further study 26 Prefill, decode and batching

Prefill processes prompt tokens; decode generates successive tokens while reading cached state. Long prompts increase prefill work and cache storage. Larger batches may improve throughput but increase waiting time or memory use. Continuous batching and paged cache management are serving strategies worth understanding conceptually; the course's simple server does not implement them.

Quantization can reduce weight memory and sometimes improve speed, but hardware, kernels, batch size and quality matter. Speculative decoding uses a draft proposal verified by another model; benefits depend on acceptance rates and system costs. Do not infer a speedup solely from a method's name.

Optional deeper study

Further study 26 Worked capacity estimate

If requests arrive at two per second and average time in the system is three seconds in a stable regime, Little's law suggests about six requests in the system on average. This does not specify a safe worker count or p95 latency: service-time variation, batching, queueing and saturation still matter. Use it as a consistency check, then measure.

Optional deeper study

Further study 26 Experiment

notebook 29 calls the local API and records a defined end-to-end latency distribution. The companion load script measures the instructional extraction service, not LLM serving throughput. Replace the generator and repeat with input/output token lengths, warm/cold state and concurrency stated. Include timeouts and failed requests in results.

Use request limits, bounded queues, dependency timeouts and cancellation. Decide how to return a partial or failed result. Streaming text does not make unsupported claims acceptable; consider whether citations can be validated before committing the answer. Keep health/readiness checks distinct from an expensive full-model query.

Exit criterion: distinguish TTFT, decode speed, throughput and end-to-end latency, then state the limits of your benchmark. Reading: R01 inference topic; R19 profiling. Tutorial: 29.
