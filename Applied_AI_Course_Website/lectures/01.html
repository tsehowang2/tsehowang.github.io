Semester 1 / Week 01

From a model to a useful system

Tutorial 01Test your understanding

The question

A developer asks, “How do I set a request timeout in version 2?” A fluent answer can still be useless: it might quote version 1, invent a parameter, or omit the relevant source. A useful assistant must choose evidence, respect the requested version, form an answer, and expose enough information for verification. Our unit of engineering is this complete interaction.

An LLM models a conditional distribution over token sequences. An application wraps it in data ingestion, retrieval, prompts, tools, validation, storage and serving. A model upgrade changes one component. It does not automatically repair missing documentation or an authorization bug. Your experience with data pipelines transfers directly to corpus lineage and index freshness, but answer quality introduces a new empirical evaluation problem.

The mechanism

Represent a system run as answer = F(question, corpus, model, prompt, tools, config). Each input must be identifiable. If the corpus or prompt changes without a version, a regression cannot be attributed. Begin with a task distribution: single-page lookup, version comparison, multi-page troubleshooting, tool calculation and questions whose answers are absent. For each, define what a correct result must contain.

Separate three measurements. Retrieval asks whether supporting evidence was found. Answer assessment asks whether claims follow from it. Task assessment asks whether the user's problem was solved. An answer may be grounded yet incomplete; retrieval may succeed while generation fails. A “good answer” score collapses these distinctions and makes debugging harder.

Worked example

Suppose a 20-question development set contains 12 lookups, 4 multi-page questions and 4 unanswerable questions. The system answers 15 questions and gets 12 right. Answered-question accuracy is 12/15 = 80%; answer coverage is 15/20 = 75%. Overall correctness depends on the refusal labels as well. If all five refusals were appropriate, that is 17/20 correct decisions; if only two were appropriate, it is 14/20. Never report selective accuracy without coverage and refusal behavior.

This week build a deterministic lexical/evidence baseline before loading a model. The starter's invented docs let you inspect every mistake. Its extraction output is intentionally limited; the baseline establishes that ingestion and evaluation work independently of generation.

Experiment and common failure

Create ten questions before changing the retriever. Write evidence IDs and expected facts yourself. Run notebook 01, inspect each result, and classify errors as missing data, wrong version, retrieval miss, unsupported claim, or unclear question. Record latency with the timing boundary explicitly stated. Do not select ten easy questions after seeing the outputs: that produces a demonstration, not an evaluation set.

Exit criterion: explain the difference between model quality and system quality, and reproduce the same baseline result from saved inputs. Reading: R02 overview; R03 evaluation topic. Lab: 01. Test: week 1.
