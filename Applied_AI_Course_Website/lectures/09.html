Notation in this lesson

B: batch · T: tokens · d_model: model width · H: query heads · H_kv: key/value heads · d_head: query/key width per head · d_value: value width per head

One view of a sentence may not be enough

In “I go to school by bus,” several relationships can matter at once. The representation may need information about the destination, the action, and the means of travel. One attention head computes one pattern of comparisons and value mixing for each query.

Multiple heads give the layer several learned projection sets. Each can form a different mixture. We should not assume that one particular head always represents “transport” and another “grammar.” Those are hypotheses to investigate in a trained model, not labels built into the architecture.

First understand multiple heads as parallel numerical computations. Their outputs are concatenated and transformed back into a representation that the next operation can use.

One notation ledger for this course

Use B for batch size, T for the number of input positions, H for query heads, d_model for the residual-stream width, d_head for each query/key head width, and d_value for each value-head width. In our standard teaching attention, d_value=d_head and H*d_head=d_model. A later grouped-query model may have fewer key/value heads H_kv than query heads H. Vocabulary size V is separate from the value matrix V; the surrounding formula or table identifies which is meant.

Splitting a representation into head computations

Suppose the model width is d_model=8 and there are H=2 heads of width 4. Each head forms Q, K, and V projections for the same sentence. For T=6 positions, one head's queries have shape [6,4], and its score matrix has shape [6,6].

Each head produces an output [6,4]. Concatenating two outputs gives [6,8]. An output projection of shape [8,8] transforms those concatenated features into the residual stream's width.

The heads do not divide the sentence into separate word groups. Both heads can operate over all allowed positions. The split concerns representation features and learned projections.

A small concatenation example

For one token, imagine head 1 produces [1,2] and head 2 produces [3,4]. Concatenation gives [1,2,3,4], not [4,6]. If the output projection is the identity matrix, that vector passes through unchanged.

If instead the first output coordinate takes the sum of the first coordinate from each head, its corresponding column can combine 1 and 3. Learned output projections let later features integrate contributions from different heads.

Concatenation and summation are different operations. Draw the feature axis before reshaping tensors. A program can have plausible shapes while joining the wrong axes.

Order is still a separate requirement

Token lookup plus unmasked self-attention, without position information, has an important symmetry: reordering the token rows reorders the corresponding outputs under the same transformation. The operation does not acquire a general notion of word order merely because we draw rows from left to right.

“The bus follows the boy” and “The boy follows the bus” need different relationships. Position information provides a way for otherwise similar token inventories to produce different representations.

A causal mask already breaks the symmetry of fully unmasked attention: different positions see different prefixes. Causal models with no explicit position encoding, often called NoPE, can learn positional information through this structure. Our teaching model uses explicit learned position embeddings, and many modern decoders use RoPE. This is an architectural choice, not a theorem that every causal decoder requires a separate position vector.

Learned absolute position embeddings

Our teaching model uses a table of position vectors. At position t, add the token embedding and the position embedding. If both have width d_model, their sum also has width d_model.

The starting representation for bus at position 5 is therefore different from bus at position 1, even before attention. The addition gives the following layers information from both token identity and position.

A learned table has a configured range of positions. Using positions beyond that range needs an explicit strategy. A model trained on short examples is not automatically reliable on much longer ones merely because its code accepts an input.

Sinusoidal and rotary ideas

Sinusoidal position encodings use functions with different frequencies rather than a learned vector for every position. The original transformer uses this construction. It supplies a structured numerical representation of position.

Rotary position methods rotate pairs of query/key coordinates by position-dependent angles. For a two-dimensional pair, rotation maps [x1,x2] to [x1 cosθ−x2 sinθ, x1 sinθ+x2 cosθ]. Relative positions can then influence dot-product comparisons.

Use different positions to see the important effect. Start with q=k=[1,0]. Rotate q by 30 degrees and k by 90 degrees. Their rotated vectors are approximately [0.8660,0.5000] and [0,1], so the dot product is 0.5. Shift both positions by another 30 degrees: the angles become 60 and 120 degrees, but the dot product remains 0.5. Their relative offset is still 60 degrees. If k instead rotates by 150 degrees while q stays at 30 degrees, the offset becomes 120 degrees and the dot product becomes −0.5. RoPE makes this relative displacement enter the comparison; real head vectors use several coordinate pairs and frequencies.

Batch and head axes

When processing B sentences together, an implementation may arrange queries as [B,H,T,d_head]. For B=2,H=2,T=6,d_head=4, this is [2,2,6,4]. Attention scores then have [2,2,6,6].

Softmax runs over the final key axis. It does not normalize across sentences or heads. Each sentence, head, and query has its own distribution over visible keys.

After value mixing, transpose and reshape carefully to return [B,T,d_model]. This is a good place for tests that use distinct values for each axis so accidental swapping becomes visible.

Worked practice and a readiness check

For d_model=12,H=3,T=6,B=2, compute d_head=4, Q shape [2,3,6,4], scores [2,3,6,6], and merged output [2,6,12]. Explain why adding a head does not necessarily mean increasing total model width.

Trace the starting representation for school at two positions under learned absolute embeddings. Then describe one difference between position vectors and the causal mask.

You are ready when head, token, batch, and feature axes have clear meanings. Next we place multi-head attention inside a transformer block, where residual connections, normalization, and nonlinear transformation complete the picture.

Position and token additions by hand

Let the token vector for school be [1,2]. Suppose position 1 has vector [0.1,0.2] and position 4 has [-0.2,0.3]. The resulting starting rows are [1.1,2.2] and [0.8,2.3].

They have the same token identity component and different position components. The following learned projections can use their combination. The addition itself has not yet mixed information from a neighboring word.

For a two-head toy layer, give each head a different projection matrix and compare its score rows. The important observation is that separate parameters allow different patterns, not that each head is guaranteed a tidy human label. When explaining a trained head, distinguish a measured pattern on examples from a general claim about every sentence.
