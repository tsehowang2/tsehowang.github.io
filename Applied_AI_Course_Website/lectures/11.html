Encoders decoders and complete model architectures

Tutorial 11Test your understanding
Lecture slides · Week 11

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

A block becomes part of a task specific arrangement

The transformer is a family of architectures built from related components. An encoder, a causal decoder, and an encoder-decoder arrangement differ in visibility and information flow.

Use three ordinary tasks. Represent the complete sentence “I go to school by bus.” Continue the prefix “I go to school by.” Translate a complete source sentence into another language. The available input and required output differ across these tasks.

The word decoder does not simply mean “something that converts IDs back into strings.” In model architecture it names a neural sequence-processing arrangement. Tokenizer decoding is a separate operation.

Start with an example

An encoder reads a complete input

For an encoder representing a fully observed sentence, valid positions can commonly attend to both earlier and later valid positions. The representation of school can use bus to its right.

That can help tasks such as labeling tokens or comparing complete inputs. A masked-language objective can hide a token and ask the model to predict it using the available surrounding text.

If we hide bus in “I go to school by [MASK],” the model's input contains a special masking situation. The training objective and input construction differ from ordinary left-to-right continuation.

Build the mechanism

A causal decoder predicts continuations

A decoder-only language model uses causal self-attention over the input prefix. At a training position, it may read the current and earlier input tokens, but not the future target token.

For “I go to school by,” the last representation produces vocabulary logits for the next token. After selecting bus, the model appends it and continues.

Many familiar text-generating LLMs use this arrangement. The architecture explains the next-token computation; later post-training shapes conversational behavior.

Build the mechanism

An encoder decoder connects two sequences

An encoder-decoder system first represents a source sequence. Its decoder then generates a target sequence while consulting both its target prefix and source representations.

The decoder's self-attention is causal over the target prefix. Its cross-attention takes queries from the decoder and keys/values from encoder outputs. Source positions need not obey the target's left-to-right order.

If the source has seven tokens and the target currently has four positions, cross-attention scores can have shape [4,7]. This rectangular matrix is the shape distinction we introduced in week 7.

Build the mechanism

A visibility table clarifies the difference

For a four-token complete input, encoder self-attention can allow all four key positions in each valid query row. For a causal decoder, row 0 sees only 0, row 1 sees 0 and 1, and so on.

Cross-attention visibility additionally depends on valid source positions and task constraints. Padding still needs handling. “Encoder sees everything” is shorthand for permitted valid input positions, not permission to ignore arbitrary constraints.

Draw the three cases instead of memorizing model-name lists. The diagrams describe what information a position can use, which is often more useful than knowing a marketing label.

Build the mechanism

Training time parallelism does not remove causality

During training, the full target sequence is available as data. A masked transformer can compute representations for many positions in parallel because the mask constrains their dependencies.

During ordinary autoregressive generation, the next generated token changes the next prefix. The model therefore proceeds sequentially across output-token decisions, even though each forward pass uses parallel numerical operations internally.

This distinguishes parallel computation within a known sequence from sequential dependence across newly generated tokens. Both can be true at the same time.

Go deeper and check understanding

Choosing the architecture for the learning exercise

Our tiny model will be a causal decoder with learned absolute positions, two blocks, and a vocabulary output head. This keeps the path close to the sentence-completion task we began with.

We are not claiming that this is the only useful architecture. We choose it because its labels, masks, and output selection can be inspected end to end.

When you later load a pretrained model, identify its architecture and tokenizer before applying assumptions from the teaching model. Different normalization, attention-head sharing, position methods, and training objectives can change important details.

Worked practice and a readiness check

For each task, identify the model arrangement and allowed context: filling a hidden word in a complete sentence, continuing an unfinished sentence, and generating a translation from a complete source.

Explain why a causal decoder cannot use the answer bus at the by position during training. Then explain why a complete-input encoder may legitimately use a word to the right of school.

You are ready when encoder, decoder, self-attention, cross-attention, training parallelism, and autoregressive generation refer to distinct operations and constraints in your explanation.

Three tasks with the same words

Task B gives “I go to school by” and asks for a continuation. It must not read an answer that has not been generated. Task C gives a source sentence and asks for a target-language sentence, requiring a relationship between two sequences.
