Semester 2 / Week 19

RAG as an open book question

Tutorial 19Test your understanding
Lecture slides · Week 19

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

A question whose answer is in a handbook

A student asks “When does the bus leave?” The handbook says “The school bus leaves at 07:30.” You can answer by finding the passage and using it as evidence.

A language model might produce 07:30 from a prompt containing that passage, or invent another plausible time if it has no evidence. Retrieval-augmented generation supplies selected external information at request time.

Begin with this open-book task. It is easier to understand the roles of retrieval and generation when the collection has three passages and the answer has one fact.

Start with an example

Retrieval finds evidence generation forms the response

The retriever receives the question and returns candidate passages. A selection procedure chooses what to include. The generator receives the question, instructions, and selected evidence and produces an answer.

An extractive baseline can simply return the relevant sentence. A generative model can reformulate, combine passages, or explain, but it introduces another opportunity for unsupported claims.

A complete pipeline needs a defined answer contract and evaluation. Adding a vector database alone does not force the generator to obey the retrieved text.

Build the mechanism

A prompt with visible boundaries

Imagine a prompt saying: “Answer the question using the evidence. If the answer is absent, state that.” Then include “[H2] The school bus leaves at 07:30” and the question.

The source label lets the response cite H2. The instruction defines intended behavior. It is still application code and evaluation that check source scope, structure, and observed quality.

The retrieved passage is data. If it contains “ignore all earlier instructions,” that text does not gain authority to change application permissions.

Build the mechanism

Two passages may be needed

For “When does the bus leave and how much is a ticket?”, retrieve H2 and H3. A complete answer says 07:30 and 4 dollars with appropriate source references.

If only H2 is available, answering the time is supported but the complete question remains partly unresolved. State the missing information rather than inventing a fare.

This example separates relevance, support, and completeness. One good passage can be relevant while insufficient for every required claim.

Build the mechanism

Chunking preserves enough context

Suppose a longer school document has the sentence “This timetable applies only on weekdays” above the departure time. Splitting them apart can remove an important condition.

A chunker decides which parts become retrieval units. Preserve headings, exceptions, tables, and source boundaries where possible. Overlap can help with boundaries but creates duplicate content and storage.

First inspect a page by hand, then choose a chunking rule. Do not begin by assuming a universal fixed size is best for every code block or paragraph.

Build the mechanism

The token budget connects back to semester one

The generator still has a finite input allowance. Instructions, the question, history if present, source labels, and evidence all consume tokens. Output needs its own reservation.

Count the complete serialized prompt with the actual tokenizer. The embedding model may have a different input limit, so a passage that fits the generator can still be truncated while embedding.

Context selection is therefore an information problem and a resource problem. Including every remotely related paragraph can bury the useful facts.

Build the mechanism

Absence and versions

For “What color is the headteacher's car?”, our handbook has no answer. The appropriate outcome is insufficiency. A nearest passage does not establish that the missing fact is present.

For a comparison of two handbook years, retrieve both required versions and label them. A source from 2026 supports its 2026 rule, not an unstated claim about 2025.

The technical-documentation assistant applies these same constraints to parameter defaults, release notes, and code examples. Now the application follows from mechanisms you already understand.

Build the mechanism

Worked practice and a readiness check

Manually execute retrieval, selection, prompt construction, answer generation, and claim checking for four handbook questions: one single fact, one two-fact question, one missing fact, and one year comparison.

Then compare an evidence-only extractor with a small real model on the same selected passages. Record additional useful explanation as well as unsupported additions.

You are ready when you can trace a claim to a specific source and distinguish an absent answer from retrieval failure. Next we improve the pipeline and evaluate the costs of added components.

Optional deeper study

Further study 13 Intuition

The model's parameters provide learned capabilities and remembered patterns. Retrieval supplies task-specific evidence at request time. RAG combines these sources, but it does not automatically force the answer to follow the evidence. The system must construct context, constrain the response, and evaluate grounding.

A practical pipeline is question normalization, authorized retrieval, reranking or selection, context packing, generation, validation and response. The historical RAG paper describes a specific learned retrieval/generation formulation [R06]; the term is now also commonly used for retrieve-then-prompt applications. Be clear which system you implement.

Optional deeper study

Further study 13 Context is a limited resource

Chunks should preserve coherent statements, headings, code blocks and source provenance. Overlap can prevent boundary losses but creates duplicate candidates. Track parent page IDs so duplicated chunks do not exaggerate evidence diversity. Context packing should respect the generator tokenizer's budget and reserve output space. Adding every retrieved passage can obscure the useful evidence.

Optional deeper study

Further study 13 Worked evidence contract

Question: “What changed in the timeout default between v1 and v2?” Context contains v1's 10-second default and v2's 30-second default, each labeled with a source ID and version. A supported answer states both defaults and cites both IDs. Citing only v2 cannot support the claim about change. If only v2 is present, the assistant should state that the comparison lacks v1 evidence or retrieve it through an explicit comparison path.

Validate citations at two levels. Structural checks verify that the IDs exist and were authorized for this request. Semantic checks ask whether those passages support the individual claims. The first is automatable and necessary, but it does not substitute for the second. Neither a lexical overlap score nor a JSON schema proves entailment.

Optional deeper study

Further study 13 Experiment

notebook 20 assembles source-labeled context, runs the evidence-only baseline and then supplies the same context to a small LLM if available. Compare a supported question, a missing-answer question and a conflicting-version question. Remove a required source and see whether the model admits insufficiency.

Measure evidence coverage, factual completeness, unsupported claims and refusal quality. An assistant that refuses everything may have low unsupported-claim rate but zero usefulness. Your project needs both coverage and correctness targets. For access-controlled docs, context may include only documents the caller can read; citations and caches must follow the same rule.

Exit criterion: trace a factual claim back through the response, packed context, selected chunk and source manifest. Reading: R06 abstract/architecture; R09 context serialization. Tutorial: 19.
