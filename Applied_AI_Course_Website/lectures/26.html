Start with an example

A trained artifact needs a comparison

Our one-word school completion task gives a simple format target. The documentation project later adds cited answers or typed tool proposals. A fine-tuning run should test a stated behavior gap rather than merely produce a checkpoint.

Keep the base model, inputs, context, decoding, and evaluator comparable. If the prompt improves too, include a prompt-only control.

An experiment can conclude that the adapter does not help. That finding is useful if the data, training, and evaluation are recorded honestly.

Start with an example

A minimal training and reload procedure

Check prepared examples and nonempty answer masks. Verify finite loss, nonzero gradients on trainable factors, and absent gradients on frozen base parameters.

Run a short pilot, save the adapter and tokenizer/config metadata, release the training instance if memory is limited, then reload against the pinned base.

Generate outputs on independent task cases. A finite reload loss is a smoke check; it does not establish that the response behavior improved.

Build the mechanism

A result with a hidden regression

Suppose valid JSON rises from 80% to 96%, but correct arguments remain weak and unsupported answers rise from 5% to 15%. The model learned one behavior while worsening another.

Inspect whether targets rewarded confident answering, omitted absence cases, or paired correct formatting with incorrect facts. More valid JSON is not a sufficient release argument.

Compare per-task outcomes and preserve new errors. Choose the stronger qualifying system rather than automatically deploying the newest artifact.

Build the mechanism

Preferences begin with a rubric

For a ticket question, prefer “3×4=12 dollars” over a confident 10-dollar answer. The preference reflects correctness under the task, not response length.

Collect preferred/rejected pairs under an explicit rubric covering evidence, completeness, valid actions, and useful explanation. Audit contradictions and uncertain labels.

An LLM teacher can generate candidate pairs, but its errors can become training targets. Human or executable checks remain important where available.

Build the mechanism

The DPO margin in a small calculation

DPO compares how the learned policy changes the relative likelihood of a preferred and rejected response compared with a reference.

If the preferred response improves by 0.4 log units relative to reference and the rejected improves by 0.1, their relative margin is 0.3. With β=2, the sigmoid input is 0.6 and the loss -ln(sigmoid(0.6)) is about 0.4375.

This calculation explains the objective's direction. It does not run preference training or guarantee that the labels encode the behavior we actually want.

Build the mechanism

Reinforcement learning and verifiable rewards

RLHF can involve a learned reward model and reinforcement-learning optimization with a reference-policy constraint. Verifiable-reward approaches use checkable outcomes such as a correct arithmetic or executable result.

A checker can still be incomplete or exploitable. Reward improvement measures success against that reward procedure, not universal reliability.

Reasoning prompts, reasoning training, preference optimization, and executable verification remain distinct interventions. State which one an experiment actually used.

Build the mechanism

Distillation and forgetting

Distillation teaches a student from a teacher's outputs, probabilities, or demonstrations. It can transfer useful behavior but also teacher errors and superficial style.

Fine-tuning a narrow task can weaken other previously useful behavior. Include general formatting, refusal, and basic instruction-following checks along with the target task.

Save raw examples, measured results, environment, and model revisions. These records make a negative or mixed result understandable instead of an unexplained “fine-tuning failed.”

Build the mechanism

Worked practice and a readiness check

Run the real small-model LoRA tutorial and a controlled base comparison. Report task quality, invalid outputs, unsupported behavior, memory, and elapsed time.

Create 20 reviewed preference pairs, explain one ambiguous preference, and reproduce the DPO scalar loss. Clearly separate that objective exercise from actual SFT training.

You are ready when you can defend a release decision using application outcomes and discuss preference/distillation methods without claiming experiments you did not run.

Further study 19 Intuition

Training loss answers whether the model is fitting its supervised targets. The application question is whether the saved adapter improves the target task without unacceptable regressions. A completed experiment includes a baseline, a controlled training run, a held-out comparison and a reproducible checkpoint.

Use the same base revision, task contexts, decoding settings and evaluation parser for base and adapted models. If you improve the prompt while adding an adapter, run a separate prompt-only control. A minimal comparison matrix is base prompt, improved prompt, improved prompt plus RAG, and RAG plus adapter, with constraints appropriate to the task. Do not demand every combination when it cannot answer the research question.

Further study 19 Training mechanics

Use a small batch, a short sequence length, gradient accumulation and checkpoints. Start with a few batches to verify valid-token counts, nonzero gradients and finite loss. Clip gradients if your chosen setup needs it. Disable inference-only caches during training when required by the model. Use the actual chat template consistently for preparation and evaluation.

Prompt loss masking must match serialization. The tutorial uses a single user message and assistant response, tokenizes the prefix and full conversation without duplicate special tokens, and checks that prefix IDs match the full prefix. Reject or redesign examples if this assumption fails. More complex multi-turn data needs a proper assistant-token mask, not a guess based on string length.

Further study 20 Intuition

SFT says “imitate this answer.” Preference data says “prefer this answer to that answer for this prompt.” These signals do not directly encode universal truth. A rater may favor a pleasant but incorrect answer, and a teacher model may produce systematic errors.

RLHF often includes a preference-derived reward model and reinforcement learning against it. A reference-policy constraint helps limit uncontrolled policy drift. RL with verifiable rewards uses checkable outcomes, such as a correct executable result, but the checker itself can be incomplete or exploitable. A high reward on a narrow checker is not proof of broad reliability.

Optional deeper study

Further study 20 DPO mechanism

DPO trains directly on preferred and rejected responses relative to a reference model. One form minimizes -log sigmoid(beta * [(log pi(y+|x)-log pi_ref(y+|x)) - (log pi(y-|x)-log pi_ref(y-|x))]). The bracket compares relative policy changes, not just raw sequence likelihoods. beta is a tuning parameter controlling this relationship; its practical effect depends on the setup.

If the preferred response improves relative to the rejected response, the loss decreases. But mislabeled preference pairs can optimize the wrong behavior. Deduplicate pairs, audit contradictory labels, and ensure answers are judged against the same context and task.

Optional deeper study

Further study 20 Distillation and forgetting

Distillation trains a student using a teacher's outputs, probabilities or demonstrations. It can transfer behavior economically, but the student may inherit teacher errors or learn superficial formatting. Record provenance and verify the teacher-generated data. Fine-tuning can also weaken previously useful behavior; evaluate general-format, refusal and basic instruction-following cases alongside the narrow task.

Optional deeper study

Further study 20 Worked comparison

A teacher produces a long explanation with a wrong API name; a shorter response cites the correct source and admits an unresolved version difference. If a preference label rewards length, the system may optimize verbosity rather than correctness. Write a rubric with factuality, evidence, completeness and action validity before collecting labels.

Optional deeper study

Further study 20 Experiment

notebook 26 includes a numerical DPO loss calculation, not a full RLHF training pipeline. Create 20 preference pairs from your development failures, label them using an explicit rubric, and check agreement on a small blinded re-labeling pass. Identify one case where a binary preference hides a meaningful tradeoff. Full DPO/RL training is an optional extension that replaces another experiment if chosen.

Exit criterion: distinguish SFT, reward-model RLHF, DPO, verifiable rewards and distillation, and explain the risk of optimizing a proxy. Reading: R15 objective; R03 post-training topic. Tutorial: 26.
