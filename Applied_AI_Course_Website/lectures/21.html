Semester 2 / Week 21

Evaluating retrieval answers and uncertainty

Tutorial 21Test your understanding
Lecture slides · Week 21

Learn one step at a time.

Read each explanation, pause to predict the result, then continue. Use the arrow keys while the presentation is focused. The complete lecture reader is below.

Start with an example

A quiz needs a marking rule

Ask the handbook assistant ten questions. Before running it, decide which facts and sources each answer requires. Otherwise it is easy to call a polished answer “good” after seeing it.

Separate retrieval evidence, answer correctness, completeness, citation support, and appropriate insufficiency. Also record failures and resource use.

The benchmark is a small specification of behavior. It can be incomplete or biased, so its design deserves the same care as the model configuration.

Start with an example

Recall hit rate and reciprocal rank

Let required evidence be {H2,H3} and retrieved results be [H1,H2,H4]. Hit@3=1 because one relevant passage appears. Recall@3=1/2 because half the required evidence appears. Reciprocal rank is 1/2 because the first relevant item is at rank 2.

For an unsupported question with no relevant passages, ordinary recall has a zero denominator. Mark it not applicable and evaluate answer/refusal behavior separately.

Do not rename hit rate as recall when multiple sources can be needed. That would hide missing evidence on the harder tasks.

Build the mechanism

An answer can be supported but incomplete

If the question asks time and fare, “The bus leaves at 07:30 [H2]” is supported but incomplete. “The bus leaves at 07:30 and costs 2 dollars [H2]” adds an unsupported fare.

A rubric should identify required facts and unsupported or contradicted claims. Exact substring matching can be a useful smoke test but will miss paraphrases, contradictions, and wrong associations.

Human review remains useful on a measured subset. Report its sample size and disagreement rather than presenting manual judgments as infallible.

Build the mechanism

Coverage and selective accuracy

Suppose the assistant answers 15 of 20 questions and 12 of those answers are correct. Accuracy among answered questions is 80%, and coverage is 75%.

Overall correctness also depends on whether the five refusals were appropriate. Refusing everything can reduce unsupported assertions while making the product useless.

Evaluate the balance under the intended task distribution. A similarity threshold is chosen on development data; it is not a probability guarantee.

Build the mechanism

Train development and held out evaluation

Training data change learned parameters. Development examples guide prompts, thresholds, chunking, and other settings. Held-out examples estimate performance after those choices.

Split by meaningful groups before generating near-duplicate questions or overlapping chunks. For RAG, the indexed reference documents remain readable at inference; leakage concerns using held-out questions or labels to choose the system.

If you tune after inspecting final test errors, label the subsequent analysis exploratory and reserve fresh untouched cases for another final claim.

Build the mechanism

Comparing two systems on the same tasks

If A solves 32/40 and B solves 34/40, the observed difference is five percentage points. Inspect paired results: which errors did B fix, and which new ones did it create?

A paired bootstrap resamples task indices and calculates the difference using matched outputs. Correlation among question families can make naive individual-task resampling optimistic.

An interval and small sample should lead to a measured statement about uncertainty. “The average is larger” does not establish a reliable improvement by itself.

Build the mechanism

Model judges and operational metrics

An LLM judge can apply a rubric at scale, but it can favor wording, length, or familiar model styles. Calibrate against reviewed examples and inspect disagreements. Version the judge and its prompt.

Record parse errors, timeouts, and budget failures. They must remain visible in the denominator or an explicitly specified outcome category.

Latency and tokens accompany quality. A method that solves two more tasks using five times the inference budget may still be useful, but the tradeoff should be stated.

Build the mechanism

Worked practice and a readiness check

Calculate the three retrieval metrics for gold {A,B} and ranking [C,A,D]. Then label a supported-incomplete answer and an unsupported-complete-looking answer.

Prepare a small frozen development evaluation, add adversarial cases, and produce per-example records. Write a release recommendation with both evidence and limitations.

You are ready when your evaluation explains where the system succeeds and fails, not merely a single judge score or attractive demonstration.

Optional deeper study

Further study 15 Intuition

Your benchmark is a small, imperfect specification of desired behavior. It should contain representative successes, difficult cases and explicit absences. A single average judge score makes release decisions hard to defend. Save the underlying examples, judgments and slices.

Partition by intended use: training/adaptation, development/tuning, and final held-out evaluation. Avoid nearly identical page families or generated paraphrases crossing boundaries when they reveal the answers. Retrieval is allowed to read the indexed reference documents at evaluation time; the leakage concern is using held-out questions, labels or near-duplicates to tune the system. Keep this distinction precise.

Optional deeper study

Further study 15 Metrics at each boundary

Evaluate retrieval with labeled evidence; answer correctness against required facts; citation validity structurally and semantically; unsupported claims; appropriate refusal; task completion; latency, tokens and failures. For an agent later, also evaluate tool correctness, forbidden actions and budget exhaustion. State denominators explicitly, including timeouts and parse errors.

An LLM judge can provide scalable rubric-based assistance, but it can be biased by wording, answer length and its own model family. Calibrate it against human-labeled examples, randomize answer ordering in pairwise comparisons, inspect disagreement, and keep the judge prompt/model version. Do not use the same model's self-confidence as the only evidence of correctness.

Optional deeper study

Further study 15 Worked uncertainty example

If system A answers 32/40 correctly and B answers 34/40 correctly, the observed difference is 5 percentage points. It is not automatically a meaningful improvement. Inspect paired differences: perhaps B fixes four A errors but creates two new ones. A paired bootstrap resamples task indices and recomputes the difference, preserving pairing. With small or correlated samples, uncertainty remains large; report intervals and assumptions instead of claiming superiority from two tasks.

Further study 15 Experiment

notebook 21 implements retrieval metrics, paired resampling and a JSON evaluation record. Add at least five adversarial cases, including version mismatch, irrelevant high-overlap evidence, missing answers, fake instructions inside a page and multi-source questions. Use development data for thresholds; run the held-out set only at the planned checkpoint.

The starter's structural tests establish software behavior and metric arithmetic. They do not establish natural-language grounding. Your manual scoring rubric must identify required facts and unsupported statements per task. Keep a short error notebook with the original question, expected evidence, actual output, diagnosis and next hypothesis.
