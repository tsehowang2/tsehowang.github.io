Tools are typed capabilities

Tutorial 11Test your understanding
Explore the mechanism

The agent and its controller

Try valid actions, unknown tools, wrong scope and an unending planner.

Enable JavaScript to use this illustration. The lecture notes below explain the same mechanism.

Intuition

A model can propose calling a calculator, looking up a document, or inspecting a configuration. It does not gain authority merely by naming a function. A tool interface specifies which operations exist, which arguments are valid, and how results are returned. Application code enforces those rules.

Define a tool by name, input schema, output schema, authorization requirements, failure states and side effects. Separate read-only tools from actions that change external state. For this course, executable tools are a bounded arithmetic calculator and a fixed configuration validator. Neither exposes arbitrary Python evaluation, shell commands, network requests or file writes.

Validation layers

Parse the model response; validate its shape; check the tool name; validate argument keys/types/ranges; enforce authorization; execute with time/resource limits; normalize the observation; log the outcome. Never use eval on model-generated expressions. The bundled calculator parses an arithmetic AST, accepts a narrow operator set and caps length, tree size and numerical magnitude. These checks are instructional, not a general sandbox for arbitrary code.

Worked contract

validate_config accepts exactly timeout_ms as an integer in a documented range and retries as an integer in a documented range. An input containing an extra command field is rejected. An integer field should not silently accept Python's boolean subtype. The observation returns valid plus explicit errors; it does not return an unstructured exception traceback to the model.

Idempotency matters for side effects. Retrying a document lookup is usually harmless; retrying a deployment may create multiple releases. A real side-effecting tool needs an idempotency key, authorization and explicit retry semantics. We study these contracts without exposing deployment tools in the starter.

Experiment

Notebook 11 exercises valid calls, unknown tools, missing arguments, oversized expressions, division by zero, extra fields and invalid value ranges. Predict whether each should be rejected before execution or reported as a tool failure. Build a small table of observable outcomes and expected traces.

The documentation assistant's useful executable behavior is narrow: calculate a retry delay from retrieved rules or validate a proposed configuration against the selected version. Generic shell access would expand risk and evaluation scope far beyond the task. Add capabilities only when an actual user task requires them.

Exit criterion: draw the boundary between a model's proposed call and authorized execution, and implement validation outside the prompt. Reading: R11 actions/observations; R03 agent/context topic. Lab: 11.
