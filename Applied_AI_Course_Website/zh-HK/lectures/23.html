完整講義

閱讀完整解說

一個 operation，很多獨立 element

取兩個各有 257 個數字的 vector，把對應 element 相加。CPU loop 很容易理解：對每個 index i，計算 c[i]=a[i]+b[i]。

CUDA kernel 可以把這種 elementwise 工作分配到 GPU 的 thread。數學結果不變；改變的是程式如何分配工作、access memory，以及量度 execution。

我們先從 vector addition 開始，而不是自行寫 attention kernel，因為在 optimization 變得複雜之前，correctness 和 indexing 必須清楚。

Thread、block 和 index

一維 kernel 可以計算 i=blockIdx.x×blockDim.x+threadIdx.x。如果一個 block 有 256 threads，兩個 block 就為 length-257 vector 提供 512 個 thread index。

i≥257 的 thread 不可 access array。Bounds check 是 correctness 的一部分，不是可以隨意刪掉的 optimization detail。

Block 可以獨立執行。不要假設普通 kernel 在整個 grid 都有通用 synchronization barrier。

Host 和 device 的責任

CPU host 分配或準備 input、管理 device memory、在需要時 transfer value、launch kernel，並取回 result。

GPU device code 執行每個 thread 的 operation。Launch kernel 不代表所有 result 馬上可供 CPU 使用；execution 可以是 asynchronous。

跟着提供的 CUDA C++ example，指出哪些 statement 屬於 allocation、transfer、launch、synchronization、timing 和 cleanup。

Memory access 和 arithmetic intensity

對 float32 vector addition，每次 addition 需要兩次 input read 和一次 output write，忽略 cache 及其他效應，約搬移十二 bytes。這屬於 low arithmetic intensity。

相鄰 thread 讀相鄰 element，可以讓 memory transaction 更有效率。分散 access，以及反覆、不必要的 transfer，都可能損害 performance。

Matrix multiplication 可以在 tile 中重用 value，在 arithmetic 和 movement 之間形成不同平衡。Kernel optimization 需要理解這種 reuse 和 device，而不是假設更多 thread 一定更快。

Warps、coalesced access 和 tensor cores

NVIDIA CUDA GPU 的 warp 包含 32 threads，以 SIMT group 執行。若相鄰 active lanes 讀取相鄰 float32 elements，通常可用較少 memory transactions 完成，比地址分散的情況有效。這稱為 coalescing。Vector addition 讓 lane i 讀取 a[i]、b[i] 並寫入 c[i]；例如 a[32*i] 的 strided access 往往浪費較多傳輸 bytes。Alignment、caching 和實際 access pattern 仍影響結果。

Tensor cores 加速指定 dtypes 和 layouts 的 matrix multiply-accumulate operations。它們並非每種 CUDA instruction 的較快替代品；vector addition 不會因為改 dtype 就變成 matrix multiplication。應以 profiler 檢查所選 kernel 和 numerical tolerance。

普通 grid 與 cooperative grid 不同

普通 kernel 不能假設所有 blocks 同時 resident，亦不能任意使用 grid-wide barrier。Cooperative Groups 可為符合 device 和 launch 限制、以 cooperative launch 啟動的 kernel 提供 grid synchronization。若不符合條件，應把需要全域次序的 stages 分成不同 launches，或使用合適的既有 algorithm。Block barrier 只協調同一 block 內參與的 threads，應放在這些 threads 能一致到達的位置。

Triton 和 torch.compile 處於不同層次

Triton kernel 使用以 Python 為基礎的 GPU programming language 表達一組 tensor work。其 vector-add tutorial 建立一組 offsets，以 mask 載入有效 elements，相加後用相同 boundary mask 儲存。這個 mask 與 CUDA bounds check 一樣，確保 length 257 的情況正確。這裏的 Triton 是 kernel language，並非 NVIDIA Triton Inference Server。

torch.compile 從 PyTorch function 或 model 出發，capture 支援的 computation，再交 compiler backend 優化；backend 可能產生 fused Triton kernels。Compilation 可減少 Python overhead 和 intermediate memory traffic，但 graph breaks 或不支援的 patterns 會限制改善。比較 warmup 後的 eager 和 compiled runs，另行報告 compilation cost，並先核對 outputs 一致再比較時間。這是在已有 profiler workflow 上增加 optimization tool，而非要求另一套 training framework。

量度 asynchronous device 的時間

如果只用 CPU clock 量度 launch，可能主要量到 dispatch。應使用 CUDA event，或在要量度的 interval 前後 synchronization。

先 warmup，重複量度，報告 median 和 spread。說明是否包括 transfer、allocation、compilation 和 first-run effect。

Kernel-only time 和 end-to-end application time 回答不同問題。診斷 optimization 是否對實際 workload 有幫助時，應保留兩者。

用 Amdahl 推理判斷實際 optimization

假設完整 task 需 20 ms，其中 kernel 佔 3 ms。即使把 kernel 加速至兩倍，總時間也只降至 18.5 ms，speedup 約 1.081。

這個計算解釋了為甚麼大幅 kernel speedup，可能只帶來有限的使用者體驗改善。應 optimize 量測任務中佔主要時間的 component。

錯誤結果不能算 speedup。報告 performance 之前，先以適當 tolerance，對照 CPU reference 驗證。

為 transformer operation 做 profiling

用 profiler 檢查 operator time、shape、memory 和 CPU/GPU activity。先用短小、可重現的 workload，並儲存 trace。

FlashAttention 示範如何重新設計 attention computation，以減少 memory traffic，同時在 numerical behavior 容許下保留其數學運算。它不是另一種 language-model objective。

Custom kernel 和 distributed training 屬於更深領域。本課必做練習建立 CUDA indexing、correctness、同步量度和 bottleneck diagnosis 的入門能力。

實例練習與學習檢查

測試 vector lengths 1、257 和一個較大值。解釋為何 257 這個不整齊的 length 很重要。改用不同 block sizes 重做，同時保留 bounds checks。

Profile 一次 matrix multiplication 或短 model pass。分開 transfer 和 execution cost，並指出一個由 trace 支持的 bottleneck。

當 performance claim 包含正確 output、timing boundary、device/software detail 和可重現 workload，就已準備好繼續。

參考細節與學習檢查

複習 A：直觀理解

PyTorch operation 最終都會執行 kernel。CUDA kernel 指定很多 thread 各自要做的工作。即使大部分 application 工作應繼續用 optimized library，親手寫一個小 kernel，也能具體理解 launch overhead、indexing、memory access 和 synchronization。

對一維 array，thread index 為 i = blockIdx.x * blockDim.x + threadIdx.x 。Vector-add kernel 計算 c[i]=a[i]+b[i] ，條件是 i<n 。當 n 不能被 block size 整除時，bounds check 很重要。Block 獨立被安排執行；code 不可假設普通 kernel 內有通用 grid-wide barrier。

複習 A：Memory 和 performance

相鄰 thread 讀相鄰 element，通常比零散 access 產生更有效率的 memory transaction。Shared memory 可以在 block 內重用 data，但 reuse 的收益必須值得付出 loading 和 synchronization overhead。參與的 thread 必須一致到達 barrier。Occupancy 是一項診斷資料，不是保證最高速度的目標。

Arithmetic intensity 約等於 operation 數除以搬移 bytes。Vector addition 每次加法有兩次 input read、一次 output write：對 float32 而言，忽略 cache 時約為每 byte 1/12 次 operation。這是 low intensity，因此提高理論 arithmetic throughput 的幫助，可能不如 memory bandwidth。Matrix multiplication 可以重用 tile，達到高得多的 intensity。

複習 A：Timing 計算例子

GPU 工作相對於 host 是 asynchronous。不做 synchronization 就量 launch，可能主要量到 dispatch。用 CUDA event，或在定義好的 measurement interval 前後 synchronization。先 warmup，再重複 operation，報告 median 和 spread。只有問題明確是 end-to-end latency 時，才把 data transfer 計入；研究 device operation 時，另外報告 kernel-only time。

假設 end-to-end time 是 20 ms，其中 kernel 佔 3 ms。Kernel 加速至兩倍後，總共是 18.5 ms，speedup 只有 1.081。這就是 Amdahl 式推理：optimize 真實任務中佔主要時間的部分。

複習 A：實驗

如果有 nvcc 和 GPU， Tutorial 23: CUDA kernels 及 profiling 會 compile 內附 vector-add example。執行 n=1、n=257 和較大 n，測試 indexing 和 overhead。以 numerical tolerance 對照 CPU reference。然後 profile PyTorch matrix multiplication 或短 transformer forward pass。儲存 trace 並解釋一個 bottleneck。FlashAttention 是更深入的例子：它重新設計 memory traffic，而非改變 attention objective [ Dao et al. FlashAttention (R26) ]。

要辨認的失敗： 把 cold first call 與已 warmed 的 library call 比較，量到的是 setup 差異。產生錯誤 value 的 benchmark，不能算 performance result。 閱讀材料： NVIDIA CUDA introduction (R17) 的 indexing example、 PyTorch profiler recipe (R19) 的 profiling；選讀 Dao et al. FlashAttention (R26) 。 Tutorial： 23.
