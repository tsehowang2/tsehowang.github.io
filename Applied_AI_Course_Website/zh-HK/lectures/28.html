閱讀完整解說

harness

Harness 是包圍 model 的 application code：準備 inputs、validate 和執行 actions、追蹤 state/budgets、記錄 outcomes。

Controller 令 agent 成為可運行 system

想像你在監督 school trip。只有一張 possible tasks 清單並不足夠；需要有人追蹤已發生甚麼，以及何時停止。Agent execution harness 就在 code 中擔任這種協調角色。

它的 state 可包含 question、allowed version、observations、evidence IDs、step count 和 status。Model 提出 action，再由 harness validation 和 execute。

Evaluation harness 的角色不同：載入 tasks、執行指定 system、檢查 outcomes，並收集 metrics。兩者都需要 versioned configuration，但不能互相取代。

一個完整小型 loop

Initialize state。向 planner 要 typed proposal。如果是 final answer，validate response contract 後停止。如果是 tool action，執行前先 validate name、schema、scope 和 bounds。

記錄 normalized observation，更新 state，並在 budget 內重複。根據實作 policy，在 invalid proposals、failures、exhaustion、timeout 或 cancellation 時明確 terminate。

每條路徑都應留下 trace。Exception 或重複 tool request，不應默默變成虛構的成功 answer。

三個 proposals 的 trace

第一個 proposal retrieve retry rule。第二個計算 cumulative delay。第三個回傳 result，並附已觀察到的 source IDs。

若 planner 不斷要求再做 calculation，三個 proposals 的 budget 最終會回傳 budget_exhausted。Controller 不會只因 model 客氣地要求就繼續。

把 citation ID 與先前 retrieved evidence 比對，是一項 structural boundary。該 passage 是否支持 final claim，仍是 evaluation 問題。

Time 與 resource limits

Step cap 限制 loop iterations，卻無法中斷 blocking network call。Call 返回後才檢查 elapsed time，不等於真正設下 call deadline。

對適當 dependencies 使用 client timeouts 和 cancellation；需要 isolation 的 execution 則使用 process/container controls。Tool output 和 model context 也要限制。

Synchronous reference controller 示範 step limits 和狹窄 arithmetic safety。它不聲稱是完整的 arbitrary-code sandbox。

MCP 連接 application 與 tool provider

MCP 即 Model Context Protocol。回想你已用過的 calculator：model 提議計算，application code 檢查 proposal，然後執行允許的 function。MCP 為 application 提供一套標準方式，以發現及呼叫另一個程式提供的 capabilities。它不會改變算術本身，亦不會取代 request validation [ Model Context Protocol architecture (R29) ]。

角色 在本例中的意思
Host 管理 model、使用者互動和 tool policy 的 documentation-assistant application。
Client host 內負責與一個 MCP server 通訊的 component。
Server 提供 calculator 並處理 request 的程式；可以在本機或遠端執行。

連線設定完成後，client 可以提出 tools/list request。server 會描述可用 tools，包括名稱和 input schemas。host 決定把哪些 tools 提供給 model。對問題「A bus ticket costs 4 dollars. What do three tickets cost?」，model 可能提議使用已有的 calculator，expression 是「3*4」。

host 檢查 proposal 後，透過其 MCP client 以 tools/call 傳送允許的 request。server 檢查 request，執行允許的計算，並傳回結果 12。host 記錄 observation，再可把結果提供給 model，組織最終答案。model proposal 和 protocol request 是不同的 representation；application code 把兩者連接起來 [ Model Context Protocol tools (R30) ]。

MCP 亦定義 resources，用於提供 handbook passage 等 context data，以及 prompts，用於提供可重用的 message templates。在這裏，分別很簡單：tool 執行指定 operation，resource 提供 context，prompt 提供可重用的互動 template。application 仍需決定如何使用它們。

比較已有的 direct function call：direct 版本由 application code 呼叫 calculator；MCP 版本則加入標準 client/server interface，以進行 discovery 和 execution。harness 仍負責 state、允許的 actions 和停止條件。透過 MCP 提供 tool，並不會自動令 arguments 有效，或令其使用獲得授權。

檢查理解：在這個例子中指出 host、client、server、model proposal、tool result 和 harness。能正確解釋這些 boundary 已足夠；本課程不要求你部署 MCP server。

Planning 方法

ReAct-style interaction 交替進行 actions 和 observations。Plan-and-execute 先提出 plan，再執行或修訂。Routing 則選擇專門 workflow。

這些模式可用不同 libraries 實作，但仍要問相同問題：甚麼 state 有權威性、哪些 actions 獲准、甚麼 observation 會改變 plan，以及甚麼會 terminate execution？

Multiple agents 會增加 coordination、重複 context、cost 和新 failure modes。它們是選做 advanced 方向，不是本 single-controller project 的先決條件。

Memory 有多種意思

目前 chat history、structured task state、retrieved documents 和 persistent user memory，各有不同 lifetime 和 trust properties。

Summary 可壓縮 text，但也可能遺漏條件。若 user 由 version 1 轉為與 version 2 比較，要明確保留該 intent，而非相信只寫 “user uses version 1.” 的 summary。

Authorization 必須來自 authenticated application state，而非 model 撰寫的 memory。把 critical constraints 和 source provenance 放在 structured fields。

Task evaluation 要檢查 traces

Final sentence 可以看似正確，卻隱藏 forbidden action 或漏做 required calculation。要量度 task success、call validity、forbidden calls、failures、budgets、latency 和 total model work。

若 agent 從不使用必需 tool，不應因 “valid-call” denominator 為空而得分。要定義 success predicates，並審核 traces。

Retries 需要有界、因 operation 而異的處理。Invalid arguments 和 non-idempotent side effects，不能像 transient read timeouts 一樣盲目 retry。

實例練習與學習檢查

使用 visual harness 嘗試 success、unknown tool、wrong version 和 endless planner 情況。然後執行真正 model planner，與 deterministic workflow 比較。

準備至少 20 個獨立檢查的 tasks，保留 successful 和 failed traces。解釋一項有用 adaptive choice 和一項不必要 action。

當 agent 是行為可觀察的 bounded state machine，而非未經檢查的 prompt-to-framework call，就已準備好。

參考細節與學習檢查

複習 A：直觀理解

Workflow 的 control path 大致預定。Agent 則讓 model outputs 影響下一 action。兩者都需要 orchestration code。當 task 要根據 observations 調整時，agentic behavior 才有用；對固定 lookup，它可能只增加不必要 overhead。

Harness 在這裏有兩個相關意思。一個 agent execution harness 管理 state、model calls、tools、budgets、observation limits、cancellation 和 termination。另一個 evaluation harness 載入 tasks、執行指定 system、記錄 results，並計算 metrics。兩者可以整合，但責任不同。明確命名兩者，可避免用含糊的 “we have a harness” 掩蓋缺失 controls。

複習 A：State 與 transition

明確表示 state：question、allowed version、evidence IDs、observations、step count、token/cost budget、status 和 error。Planner 提出 tool action 或 final response。Controller validation，execute allowed actions，並更新 state。Termination reasons 包括 success、invalid proposal、tool failure、step exhaustion、timeout 和 cancellation。每條路徑都必須可觀察。

複習 A：Trace 實例

Step 1 retrieve retry rules。Step 2 用 bounded expression 呼叫 calculator。Step 3 以 numerical result 和 source IDs 作答。失敗 calculator call 不應永遠重複。如果 planner 最多有三步，而最後一步 proposal 仍需要下一 observation，應明確以 budget-exhausted status 結束，而非虛構 final answer。

Wall-clock limits 需要真正 enforce。Blocking call 返回後才檢查 elapsed time，無法中斷該 call。Network tools 用 client timeouts；untrusted execution 用 process/container limits。我們的 synchronous starter enforce step limits 和 arithmetic bounds；deployment extension 則需要 per-call timeout/cancellation implementations。

複習 A：實驗

Tutorial 27: Tool、function、workflow 與 agent 讓 deterministic planner 經 controller 執行，以測試 execution contract。這是 controller fixture，不是 LLM planning 的證據。 Tutorial 28: Harness、planning、memory 與有界執行 連接真正 model planner。注入永不停止、回傳 malformed JSON，以及虛構 tool 的 planners。驗證明確 terminal states 和有限 tool calls。

對每條 trace，問展示給 model 的資訊是否必要。大型 tool outputs 可令 context overflow，亦可能帶有 adversarial instructions。限制並標記 observations，另存 authoritative metadata，不要把 tool text 當成新 policy。

完成標準： 實作 bounded state machine，並區分 execution 和 evaluation harnesses。 閱讀材料： Yao et al. ReAct (R11) ； Hung-yi Lee Introduction to GenAI and ML 2025 (R03) context engineering 主題。 Tutorial： 28.

複習 B：直觀理解

Agent 的 “memory” 可指目前 prompt、task scratch state、retrieved documents，或過去 interactions 的 persistent store。它們的 retention 和 trust properties 不同。記住更多 text，不代表 context 一定更有用。

用 typed task state 保存 requested version、selected source IDs 和 tool outcomes 等 facts。Summaries 可壓縮長 histories，但可能遺漏 exception，或把不確定 observation 變成自信 assertion。把 critical constraints 保留於 structured fields，並保留 source provenance。

複習 B：Planning 模式

ReAct-style systems 交替進行 action selection 和 observations。Plan-and-execute 先產生 plan，再執行，並可能在 observations 不符時修訂。Routing 選擇專門 workflow。Multi-agent systems 分配 roles，但增加 coordination、重複 context、cost 和 evaluation complexity。本課程核心是單一 bounded controller，不要求 multi-agent implementation。

Versioned lookup 的固定 workflow 可以是 retrieve、pack、answer 和 validate。Troubleshooting task 則可能受惠於 conditional actions：inspect version、retrieve rule、validate config，再解釋第一項違反 requirement 的地方。後者提供 adaptive planning 的具體理由。

複習 B：Memory 失敗實例

User 先問 v1，再說 “now compare that with v2.” 若 summary 只儲存 “user uses v1”，下一次 retrieval 可能 filter 掉 v2。要明確保留 task allowed versions 和 comparison intent。Authorization 應來自 authenticated application state，絕不能來自 conversational memory 或 model-generated summaries。

複習 B：實驗

Tutorial 28: Harness、planning、memory 與有界執行 把小 model 的 JSON proposal 轉成 controller action。在相同 lookups、calculations 和 troubleshooting tasks 上，與固定 workflow 比較。統計 invalid proposals、不必要 tool calls、漏做 required actions、completion、latency 和 total model tokens。小 model 可能經常失敗；用這些 traces 決定哪些情況應採 deterministic route。

測試一個長而無關的 observation，以及 retrieved page 中的 misleading instruction。驗證 policy fields 不在 model 權限內。失敗 model proposal 必須產生受控 result，不可改為執行猜測 arguments。

完成標準： 為特定 task 解釋 adaptive planning 的理由，並指出哪些 state 應放在 structured memory。 閱讀材料： Yao et al. ReAct (R11) ； Hung-yi Lee Introduction to GenAI and ML 2025 (R03) context engineering。 Tutorial： 28.

複習 C：直觀理解

有說服力的 final sentence 可能掩蓋失敗或 forbidden action。Agent evaluation 必須檢查 environment 和 trace，不能只為 final text 評分。對 read-only tools，correctness 包括選對 evidence 和 calculation。對未來 side-effect extension，亦包括 final state，以及沒有非預期 changes。

定義 task 的 initial state、allowed actions、expected results 和 success predicates。比較 model-only answer、fixed tool workflow 和 adaptive controller。保持 tool affordances 和 budgets 可比較。Agent 有十次機會、workflow 只有一次時，不能不報告差異就比較。

複習 C：Metrics 與復原

Task success、valid-call rate、forbidden-action rate、tool failures、step count、budget exhaustion 和 cost 互相補充。從不 call tool 的 system，可能在空 denominator 上得到完美 valid-call rate；要報告使用 tools 的頻率，以及 tasks 是否需要它們。Failures 應分類，令分析能區分 planning、validation、execution 和 answer errors。

Retries 必須有界且適當。Transient read timeout 可能值得一次 backoff/retry。重複 invalid arguments 不會修復 schema。Non-idempotent side effect 不可盲目 retry。Circuit breaker 限制對失敗 dependency 的重複 calls，但不能取代正確 per-request handling。

複習 C：審核實例

Agent 完成 18/20 tasks，但其中一個成功 task 含 unauthorized call，剛好只回傳無害 data。在 zero-forbidden-action release gate 下，它不合格。另一 system 完成 17/20、沒有 violations，並清楚回報三次 controlled failures。視乎 requirements，後者可能才是可部署 candidate。Evaluation 前先定義 gate。

複習 C：實驗

建立至少 20 個有 deterministic checkers 的 tool tasks，包含 division by zero、unknown tool、wrong version、invalid config、misleading documentation 和強制 step-limit failure。執行 Tutorial 28: Harness、planning、memory 與有界執行 ，保留完整 action/observation traces，並手動審核 sample。即使 final answer 看似合理，也要報告 failure counts。

對 open-ended troubleshooting，使用 rubric 加 manual review，不要假裝一個 exact string 就能代表成功。Project report 應包含一個 agent 增加價值的 case，以及一個固定 workflow 更簡單而同樣有效的 case。若 agent 從未改善 tasks，可保留為經 evaluation 的 experimental branch，不必成為 default product。

完成標準： 利用 trace-level evidence 和 recovery behavior，支持 agent release decision。 閱讀材料： Stanford CS329S Machine Learning Systems Design (R02) stakeholder requirements； Yao et al. ReAct (R11) task/action evaluation。 Tutorial： 28.
