閱讀每段解說，停下來預測結果，然後繼續。選取簡報後，可用方向鍵操作。完整講義在下方。

由例子開始

Controller 令 agent 成為可運行 system

想像你在監督 school trip。只有一張 possible tasks 清單並不足夠；需要有人追蹤已發生甚麼，以及何時停止。Agent execution harness 就在 code 中擔任這種協調角色。

它的 state 可包含 question、allowed version、observations、evidence IDs、step count 和 status。Model 提出 action，再由 harness validation 和 execute。

Evaluation harness 的角色不同：載入 tasks、執行指定 system、檢查 outcomes，並收集 metrics。兩者都需要 versioned configuration，但不能互相取代。

由例子開始

一個完整小型 loop

Initialize state。向 planner 要 typed proposal。如果是 final answer，validate response contract 後停止。如果是 tool action，執行前先 validate name、schema、scope 和 bounds。

記錄 normalized observation，更新 state，並在 budget 內重複。根據實作 policy，在 invalid proposals、failures、exhaustion、timeout 或 cancellation 時明確 terminate。

每條路徑都應留下 trace。Exception 或重複 tool request，不應默默變成虛構的成功 answer。

建立對機制的理解

三個 proposals 的 trace

第一個 proposal retrieve retry rule。第二個計算 cumulative delay。第三個回傳 result，並附已觀察到的 source IDs。

若 planner 不斷要求再做 calculation，三個 proposals 的 budget 最終會回傳 budget_exhausted。Controller 不會只因 model 客氣地要求就繼續。

把 citation ID 與先前 retrieved evidence 比對，是一項 structural boundary。該 passage 是否支持 final claim，仍是 evaluation 問題。

建立對機制的理解

Time 與 resource limits

Step cap 限制 loop iterations，卻無法中斷 blocking network call。Call 返回後才檢查 elapsed time，不等於真正設下 call deadline。

對適當 dependencies 使用 client timeouts 和 cancellation；需要 isolation 的 execution 則使用 process/container controls。Tool output 和 model context 也要限制。

Synchronous reference controller 示範 step limits 和狹窄 arithmetic safety。它不聲稱是完整的 arbitrary-code sandbox。

建立對機制的理解

Planning 方法

ReAct-style interaction 交替進行 actions 和 observations。Plan-and-execute 先提出 plan，再執行或修訂。Routing 則選擇專門 workflow。

這些模式可用不同 libraries 實作，但仍要問相同問題：甚麼 state 有權威性、哪些 actions 獲准、甚麼 observation 會改變 plan，以及甚麼會 terminate execution？

Multiple agents 會增加 coordination、重複 context、cost 和新 failure modes。它們是選做 advanced 方向，不是本 single-controller project 的先決條件。

建立對機制的理解

Memory 有多種意思

目前 chat history、structured task state、retrieved documents 和 persistent user memory，各有不同 lifetime 和 trust properties。

Summary 可壓縮 text，但也可能遺漏條件。若 user 由 version 1 轉為與 version 2 比較，要明確保留該 intent，而非相信只寫 “user uses version 1.” 的 summary。

Authorization 必須來自 authenticated application state，而非 model 撰寫的 memory。把 critical constraints 和 source provenance 放在 structured fields。

建立對機制的理解

Task evaluation 要檢查 traces

Final sentence 可以看似正確，卻隱藏 forbidden action 或漏做 required calculation。要量度 task success、call validity、forbidden calls、failures、budgets、latency 和 total model work。

若 agent 從不使用必需 tool，不應因 “valid-call” denominator 為空而得分。要定義 success predicates，並審核 traces。

Retries 需要有界、因 operation 而異的處理。Invalid arguments 和 non-idempotent side effects，不能像 transient read timeouts 一樣盲目 retry。

建立對機制的理解

實例練習與學習檢查

準備至少 20 個獨立檢查的 tasks，保留 successful 和 failed traces。解釋一項有用 adaptive choice 和一項不必要 action。

當 agent 是行為可觀察的 bounded state machine，而非未經檢查的 prompt-to-framework call，就已準備好。

深入學習 24：直觀理解

有說服力的 final sentence 可能掩蓋失敗或 forbidden action。Agent evaluation 必須檢查 environment 和 trace，不能只為 final text 評分。對 read-only tools，correctness 包括選對 evidence 和 calculation。對未來 side-effect extension，亦包括 final state，以及沒有非預期 changes。

定義 task 的 initial state、allowed actions、expected results 和 success predicates。比較 model-only answer、fixed tool workflow 和 adaptive controller。保持 tool affordances 和 budgets 可比較。Agent 有十次機會、workflow 只有一次時，不能不報告差異就比較。

選讀：深入學習

深入學習 24：Metrics 與復原

Task success、valid-call rate、forbidden-action rate、tool failures、step count、budget exhaustion 和 cost 互相補充。從不 call tool 的 system，可能在空 denominator 上得到完美 valid-call rate；要報告使用 tools 的頻率，以及 tasks 是否需要它們。Failures 應分類，令分析能區分 planning、validation、execution 和 answer errors。

Retries 必須有界且適當。Transient read timeout 可能值得一次 backoff/retry。重複 invalid arguments 不會修復 schema。Non-idempotent side effect 不可盲目 retry。Circuit breaker 限制對失敗 dependency 的重複 calls，但不能取代正確 per-request handling。

選讀：深入學習

深入學習 24：審核實例

Agent 完成 18/20 tasks，但其中一個成功 task 含 unauthorized call，剛好只回傳無害 data。在 zero-forbidden-action release gate 下，它不合格。另一 system 完成 17/20、沒有 violations，並清楚回報三次 controlled failures。視乎 requirements，後者可能才是可部署 candidate。Evaluation 前先定義 gate。

選讀：深入學習

深入學習 24：實驗

建立至少 20 個有 deterministic checkers 的 tool tasks，包含 division by zero、unknown tool、wrong version、invalid config、misleading documentation 和強制 step-limit failure。執行 notebook 28，保留完整 action/observation traces，並手動審核 sample。即使 final answer 看似合理，也要報告 failure counts。

對 open-ended troubleshooting，使用 rubric 加 manual review，不要假裝一個 exact string 就能代表成功。Project report 應包含一個 agent 增加價值的 case，以及一個固定 workflow 更簡單而同樣有效的 case。若 agent 從未改善 tasks，可保留為經 evaluation 的 experimental branch，不必成為 default product。

完成標準： 利用 trace-level evidence 和 recovery behavior，支持 agent release decision。 閱讀材料： R02 stakeholder requirements；R11 task/action evaluation。 Tutorial： 28.

User 先問 v1，再說 “now compare that with v2.” 若 summary 只儲存 “user uses v1”，下一次 retrieval 可能 filter 掉 v2。要明確保留 task allowed versions 和 comparison intent。Authorization 應來自 authenticated application state，絕不能來自 conversational memory 或 model-generated summaries。

深入學習 23：實驗

notebook 28 把小 model 的 JSON proposal 轉成 controller action。在相同 lookups、calculations 和 troubleshooting tasks 上，與固定 workflow 比較。統計 invalid proposals、不必要 tool calls、漏做 required actions、completion、latency 和 total model tokens。小 model 可能經常失敗；用這些 traces 決定哪些情況應採 deterministic route。

測試一個長而無關的 observation，以及 retrieved page 中的 misleading instruction。驗證 policy fields 不在 model 權限內。失敗 model proposal 必須產生受控 result，不可改為執行猜測 arguments。

完成標準： 為特定 task 解釋 adaptive planning 的理由，並指出哪些 state 應放在 structured memory。 閱讀材料： R11；R03 context engineering。 Tutorial： 28.

深入學習 24：直觀理解

有說服力的 final sentence 可能掩蓋失敗或 forbidden action。Agent evaluation 必須檢查 environment 和 trace，不能只為 final text 評分。對 read-only tools，correctness 包括選對 evidence 和 calculation。對未來 side-effect extension，亦包括 final state，以及沒有非預期 changes。

定義 task 的 initial state、allowed actions、expected results 和 success predicates。比較 model-only answer、fixed tool workflow 和 adaptive controller。保持 tool affordances 和 budgets 可比較。Agent 有十次機會、workflow 只有一次時，不能不報告差異就比較。

深入學習 24：Metrics 與復原

Task success、valid-call rate、forbidden-action rate、tool failures、step count、budget exhaustion 和 cost 互相補充。從不 call tool 的 system，可能在空 denominator 上得到完美 valid-call rate；要報告使用 tools 的頻率，以及 tasks 是否需要它們。Failures 應分類，令分析能區分 planning、validation、execution 和 answer errors。

Retries 必須有界且適當。Transient read timeout 可能值得一次 backoff/retry。重複 invalid arguments 不會修復 schema。Non-idempotent side effect 不可盲目 retry。Circuit breaker 限制對失敗 dependency 的重複 calls，但不能取代正確 per-request handling。

深入學習 24：審核實例

Agent 完成 18/20 tasks，但其中一個成功 task 含 unauthorized call，剛好只回傳無害 data。在 zero-forbidden-action release gate 下，它不合格。另一 system 完成 17/20、沒有 violations，並清楚回報三次 controlled failures。視乎 requirements，後者可能才是可部署 candidate。Evaluation 前先定義 gate。

深入學習 24：實驗

建立至少 20 個有 deterministic checkers 的 tool tasks，包含 division by zero、unknown tool、wrong version、invalid config、misleading documentation 和強制 step-limit failure。執行 notebook 28，保留完整 action/observation traces，並手動審核 sample。即使 final answer 看似合理，也要報告 failure counts。

對 open-ended troubleshooting，使用 rubric 加 manual review，不要假裝一個 exact string 就能代表成功。Project report 應包含一個 agent 增加價值的 case，以及一個固定 workflow 更簡單而同樣有效的 case。若 agent 從未改善 tasks，可保留為經 evaluation 的 experimental branch，不必成為 default product。

完成標準： 利用 trace-level evidence 和 recovery behavior，支持 agent release decision。 閱讀材料： R02 stakeholder requirements；R11 task/action evaluation。 Tutorial： 28.
