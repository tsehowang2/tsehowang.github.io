從 word vector 到 semantic search

練習 17檢查你的理解
課堂投影片 · 第 17 週

一步一步學習。

閱讀每段解說，停下來預測結果，然後繼續。選取簡報後，可用方向鍵操作。完整講義在下方。

由例子開始

一本簡單的學校手冊

想像手冊有三段內容。H1 寫着 “School opens at 08:00.”，H2 寫着 “The school bus leaves at 07:30.”，H3 寫着 “A bus ticket costs 4 dollars.”。一名學生問：“When does school start?”

Search 的任務，是為這條問題選出有用的段落。問題用了 start，H1 卻用了 opens。完全相同的字詞比對可以找到 school，但也可能找到關於 bus 的段落。好的 representation 應有助分辨真正有用的 evidence 和只是相關的文字。

我們刻意先學 representation 和 transformer，才開始這個應用。現在，“embed the question” 指的是一種具體的數值運算，而不是未加解釋、像魔法一樣的 API。

由例子開始

先建立 lexical baseline

Lexical retriever 比較字詞或 term。Inverted index 把一個 term 對應到包含它的段落。Term weighting 可以減低常見字詞的影響，並強調更有辨識力的 term。

對於 school 何時開始這條問題，簡單的 overlap 方法可能同時給 H1 和 H2 分數。這種失敗不難理解：方法沒有學過 start 與 opens 的關係，也可能無法清楚分辨主要主題。

BM25 是常用的 lexical scoring 方法系列，包含 term-frequency saturation 和 length normalization。我們會把它與 semantic 方法比較，而不會假設 neural vector 對所有 query 都更好。遇到精確的 API 名稱和 error code 時，準確的 lexical matching 往往很有幫助。

建立對機制的理解

Sentence embedding 為特定任務表示輸入

Transformer encoder 可以產生帶有 context 的 token vector。Pooling 或其他 representation 程序會建立 passage 或 sentence vector。之後，training 會鼓勵這些 vector 形成適合目標比較任務的 geometry。

為 retrieval 訓練的 embedding model，目標是讓相關的 question-passage pair 在選定的 similarity function 下取得好分數。隨意平均 token row 是另一種方法，有不同的限制。

在 bi-encoder 中，question 和 passage 可以獨立 encode。Passage vector 只需儲存一次，之後可重複用於很多問題。這種重用解釋了為甚麼 dense retrieval 能擴展，而不必對每條 query 都重新與每個 passage 一起處理。

建立對機制的理解

一個小型數值排名例子

使用人為設定、已 normalize 的 question q=[1,0]。假設手冊的 vector 是 H1=[0.9,0.436]、H2=[0.6,0.8]、H3=[0,1]；第一個 vector 經過四捨五入，因此視為近似值。它們與 q 的 dot product 約為 0.9、0.6、0。

H1 排第一。這些座標是為了方便計算而設計，並非真實 embedding model 的量測輸出。給定 vector 後，排名運算是確定的；但 vector 是否表達了正確的 relevance，仍需要實驗驗證。

在 tutorial 中，以真實 model embedding 取代人為座標。固定 question set 和 evidence label，讓實驗測試 representation 本身，而不是一個精心挑選的示範。

建立對機制的理解

Retrieval embedding 可以怎樣訓練

Positive pair 由一條 question 和一段能支持答案的 passage 組成；negative pair 則不能支持答案。Contrastive objective 可以提高 positive score 相對於其他競爭分數的值。

Hard negative 與問題相似，但答案不對。對 “When does school open?” 而言，bus 的 departure time 就是有用的干擾項。另一個例子，是描述不同年份 school opening time 的段落。

如果被標為 negative 的 passage 其實提供有用 evidence，就出現 false negative。因此 dataset 的建立方式很重要。Embedding space 反映 objective 和 label，並不是客觀、通用的「意思量尺」。

建立對機制的理解

Relevance 需要 label 和明確定義

對原本的問題，H1 是 relevant。對 “How much does the school bus cost and when does it leave?”，H2 和 H3 都是必需的。只有一段相關 passage，未必足以完成整個任務。

Hit@k 問的是前 k 個結果中，是否至少有一段 relevant passage。Recall@k 問的是所有必需的 relevant passage 中，有多少比例被找出。我們會在第 21 週仔細計算兩者。

對於 “What color is the headteacher's car?” 這類沒有支持資料的問題，這本小手冊沒有對應 passage。Retriever 仍可以回傳最近的 vector；但「最近」不代表「足夠」。

建立對機制的理解

逐步轉向 technical documentation

當 passage 描述 API parameter 而非學校時間表時，結構一樣適用。精確名稱、version constraint 和 code block 會變得重要。容易理解的手冊例子先教機制，documentation corpus 再提供較難的情境。

選定一個固定的 corpus revision，保留 passage ID 和 source provenance。Question label 要與 training 或 configuration tuning 分開。不要在看到新 retriever 擅長哪些問題之後，才挑選 evaluation question。

實例練習與學習檢查

分別以 lexical search 和真正的 dense search，比較一條 paraphrase question 及一條 exact identifier question。儲存原始排名，並為每種方法記錄一個失敗例子。

深入研習 11：直觀理解

Retriever 必須把有用 evidence 排在前面，而不只是找出相關文字。精確的 API 名稱和 error code 較適合 lexical matching；改寫過的意圖可能較適合 semantic matching。先準備這兩類問題和簡單 baseline。選擇 scoring 方法，是因為它針對已觀察到的失敗，而不是因為名字有 “vector”。

選讀：深入學習

深入研習 11：Relevance 與 metric

設 G 為 relevant evidence ID 的集合，Rk 為首 k 個回傳 ID。Recall@k 為 |G intersection Rk| / |G|。只要有任何 relevant item，Hit@k 就是 1。Reciprocal rank 為 1/r，其中 r 是第一個 relevant 結果的排名；若沒有則為 0。當 relevant passage 不只一段時，Hit@k 和 Recall@k 回答的是不同問題。只要定義好 relevance label 和 normalization，NDCG 可以表示不同程度的 relevance 及位置折扣。

選讀：深入學習

深入研習 11：計算例子

假設 G={A,B}，首三個結果是 C,A,D，則 Hit@3=1、Recall@3=1/2、reciprocal rank=1/2。報告如果把 Hit@3 稱為 “recall”，就會掩蓋缺少第二段 evidence 的問題。若比較任務需要兩個 version，缺少這段 evidence 可能令問題根本無法作答。

對沒有 relevant evidence、無法回答的問題，一般 recall 的分母是 0。不要默默當作 perfect recall。應以 refusal、false-positive retrieval 或 unsupported-answer measure，另外評估這類問題。Starter 把它們的 retrieval metric 標為不適用。

深入研習 11：實驗

分清 model failure 和 ingestion failure。檢查預期 passage 是否真的在 index 裏、truncation 有沒有刪去關鍵句，以及 metadata filter 是否排除了它。真正的 capstone 要標示足夠多類問題，避免單一例子主導某個 slice。小型 teaching fixture 用來協助檢查 software correctness，並不足以充當 research dataset。
