完整講義

閱讀完整解說

答案就在手冊裏的問題

一名學生問 “When does the bus leave?”。手冊寫着 “The school bus leaves at 07:30.”。你可以先找到該 passage，再用它作 evidence 回答。

如果 prompt 包含該 passage，language model 可能產生 07:30；如果沒有 evidence，也可能捏造另一個看似合理的時間。Retrieval-augmented generation 在 request time 提供經挑選的外部資料。

先從這個開卷任務開始。當 collection 只有三段 passage，而答案只含一個 fact 時，retrieval 和 generation 的角色就更容易理解。

Retrieval 找 evidence，generation 組織回答

Retriever 收到 question，回傳 candidate passage。Selection 程序決定納入哪些內容。Generator 收到 question、instruction 和經挑選的 evidence，然後產生 answer。

Extractive baseline 可以直接回傳相關句子。Generative model 可以改寫、整合 passage 或解釋，但也多了一個加入 unsupported claim 的機會。

完整 pipeline 需要清楚定義的 answer contract 和 evaluation。單是加入 vector database，並不會迫使 generator 遵守 retrieved text。

邊界清楚的 prompt

想像 prompt 寫着：“Answer the question using the evidence. If the answer is absent, state that.”，之後放入 “[H2] The school bus leaves at 07:30” 和問題。

Source label 讓 response 可以引用 H2。Instruction 定義預期行為，但 source scope、structure 和實際 quality，仍然要由 application code 和 evaluation 檢查。

Retrieved passage 是 data。如果當中包含 “ignore all earlier instructions”，這段文字不會因此取得修改 application permission 的權限。

可能需要兩段 passage

對 “When does the bus leave and how much is a ticket?”，要找出 H2 和 H3。完整答案應說明 07:30 和 4 dollars，並附上適當 source reference。

如果只有 H2，回答時間是有支持的，但整條問題仍有部分未解決。應說明缺少甚麼資料，而不是捏造 fare。

這個例子分開了 relevance、support 和 completeness。一段好的 passage 可以 relevant，卻不足以支持所有必需 claim。

Chunking 要保留足夠 context

假設較長的 school document 在 departure time 上方寫着 “This timetable applies only on weekdays”。把兩句切開，可能令重要條件遺失。

Chunker 決定哪些部分成為 retrieval unit。應盡可能保留 heading、exception、table 和 source boundary。Overlap 有助處理邊界，但會製造重複內容並增加 storage。

先親手檢查一頁，再選 chunking rule。不要一開始就假設某個通用 fixed size 最適合所有 code block 或 paragraph。

以具體 timetable 選擇 chunk boundaries

考慮三行 source：「Weekday service」、「The school bus leaves at 07:30」和「On Friday it leaves at 07:15.」。關於 Friday 的問題需要 exception 及 heading。Fixed character cut 若把最後兩行分開，可能隱藏 exception；短 overlap 或可重新連接，但亦可能在多個 results 重複它。

策略 本例的 retrieval unit 要檢查甚麼
Fixed tokens 加 overlap 有上限的 token window，邊界 tokens 重複 Exception 和 subject 是否仍在一起
Sentence 或 heading aware Timetable heading 加相關 sentences 長 section 仍需要 size limit
Structure aware Table 連同 column headers、row labels 和 units 數字是否仍對應正確 day 和 route
Parent-child Retrieve 短小 Friday child；提供其 timetable parent Parent 是否放得入最終 context budget

假設教學 budget 是 600 tokens：instructions 和 question 預留 100、answer 預留 150、labels 和 formatting 預留 50，則 evidence 剩下 300。應在餘額內選擇完整有用 chunks；三個 100-token chunks 放得入，但 retrieved child 的 parent 可能有 400 tokens，便要選較小 section。這些是例子的 budgeted token counts，並非前三句英文的實測長度。

Token budget 接回第一學期的內容

Generator 的 input allowance 仍然有限。Instruction、question、可能存在的 history、source label 和 evidence 都消耗 token。Output 也需要預留空間。

用實際 tokenizer 計算完整 serialized prompt。Embedding model 可能有另一個 input limit，所以 passage 即使放得進 generator，在 embedding 時仍可能被 truncate。

因此 context selection 同時是 information problem 和 resource problem。加入所有稍有關係的 paragraph，可能反而埋沒有用 fact。

沒有答案與 version 的問題

對 “What color is the headteacher's car?”，手冊並沒有答案。合適結果是指出資料不足。最近的 passage，不能證明當中有那個缺失的 fact。

比較兩個年份的手冊時，要找出兩個必需 version 並清楚標示。2026 source 支持的是其 2026 規則，而不是未明說的 2025 claim。

Technical-documentation assistant 把同樣 constraint 用於 parameter default、release note 和 code example。至此，application 是建基於你已理解的機制。

實例練習與學習檢查

為四條手冊問題手動執行 retrieval、selection、prompt construction、answer generation 和 claim checking：單一 fact、兩個 fact、缺失 fact，以及年份比較各一條。

然後在相同 selected passage 上，比較 evidence-only extractor 和一個小型真實 model。既記錄額外有用的解釋，也記錄沒有支持的新增內容。

當你能把 claim 追溯至特定 source，並分辨答案不存在和 retrieval failure，就已準備好繼續。接下來會改善 pipeline，並評估新增 component 的代價。

參考細節與學習檢查

複習 A：直觀理解

Model parameter 提供學到的能力和記住的 pattern。Retrieval 在 request time 提供針對任務的 evidence。RAG 結合兩者，但不會自動迫使 answer 依循 evidence。System 必須建立 context、約束 response，並評估 grounding。

實際 pipeline 包括 question normalization、authorized retrieval、reranking 或 selection、context packing、generation、validation 和 response。原始 RAG 論文描述一種特定、透過學習整合 retrieval/generation 的 formulation [ Lewis et al. Retrieval Augmented Generation (R06) ]；現在此詞亦常用來指 retrieve-then-prompt application。要說清楚自己實作的是哪種 system。

複習 A：Context 是有限資源

Chunk 應保留連貫陳述、heading、code block 和 source provenance。Overlap 可以避免邊界資訊遺失，但會產生重複 candidate。追蹤 parent page ID，避免重複 chunk 誇大 evidence diversity。Context packing 要遵守 generator tokenizer 的 budget，並預留 output 空間。加入每一段 retrieved passage，可能反而掩蓋有用 evidence。

複習 A：Evidence contract 例子

問題是：“What changed in the timeout default between v1 and v2?”。Context 包含 v1 的 10-second default 和 v2 的 30-second default，各自標有 source ID 和 version。有支持的 answer 應列出兩個 default，並引用兩個 ID。只引用 v2 不能支持關於 change 的 claim。如果只有 v2，assistant 應指出比較缺少 v1 evidence，或透過明確 comparison path 去 retrieval。

在兩個層面驗證 citation。Structural check 確認 ID 存在，而且本次 request 獲授權使用。Semantic check 則問 passage 是否支持各個 claim。前者可自動化而且必需，但不能取代後者。Lexical overlap score 和 JSON schema 都不能證明 entailment。

複習 A：實驗

Tutorial 20: 改善 RAG，同時保留基本任務 組合附 source label 的 context，執行 evidence-only baseline，然後在資源允許時，把相同 context 交給小型 LLM。比較有支持的問題、沒有答案的問題，以及 version 衝突的問題。移除一個必需 source，觀察 model 是否承認資料不足。

量度 evidence coverage、factual completeness、unsupported claim 和 refusal quality。甚麼都拒答的 assistant，unsupported-claim rate 可能很低，但 usefulness 是零。Project 同時需要 coverage 和 correctness target。對有 access control 的 docs，context 只能包含 caller 可讀的 document；citation 和 cache 也必須遵守相同規則。

完成標準： 把 factual claim 從 response 追溯至 packed context、selected chunk 和 source manifest。 閱讀材料： Lewis et al. Retrieval Augmented Generation (R06) 的 abstract/architecture； Hugging Face Transformers chat templates (R09) 的 context serialization。 Tutorial： 19.
