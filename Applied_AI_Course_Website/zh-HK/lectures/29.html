由例子開始

儲存的 model 與運行中的 service

Notebook 在你執行 cells 時運作。Service 則接受 callers 的 requests、管理 resources，並在失敗時仍回傳已定義 responses。

Documentation assistant 的 request 需要 question 和 scope；response 需要 answer/status、citations 和 release identity。所選 model 只是 service 內的一項 dependency。

先從 local loopback API 開始。Public hosting 帶來額外 access、resource 和 infrastructure requirements，應明確實作和描述。

由例子開始

定義 release 的 artifacts

Release 依賴 sources、chunker、embedding model、index、generator、tokenizer、adapter（如有使用）、prompt、tool schemas 和 environment。

Prompt 改變即使不改 weights，也可改變 behavior。Embedding 改變通常需要相容的新 vectors/index。Source deletion 會影響下游 evidence，亦可能影響 caches。

MLOps 管理 model-dependent systems 的 development、provenance、evaluation 和 operation。LLMOps 則強調這個場景中特有的 prompt、retrieval 和 tool dependencies。

建立對機制的理解

Run manifest

記錄 source hashes、model/tokenizer revisions、index identity、prompt hash、tool version、decoding settings、code/environment、seed（如適用），以及 raw outputs。

Manifest 協助其他人重現 evaluation 過的 configuration。Content hash 識別 bytes，但不證明 quality 或 permissions。

不要把 secret values 放入 manifest 或 source repository。另行記錄所需 secret names 和 environment setup。

建立對機制的理解

Request handling

Validate input size 和 schema、apply scope controls、在 limits 下執行 retrieval 和 generation、validate result，再回傳受控 status。

使用 bounded queues，以及適當 dependency timeouts/cancellation。Health check 不應要求完整昂貴 model query；readiness 則可能需要確認 required artifacts 可用。

教學 API 是一個起始 contract，不是 multi-tenant authentication 或 production capacity 的證據。

建立對機制的理解

Prefill 與 decode

Prompt processing 通常稱為 prefill。之後的 autoregressive steps 利用 cached state，decode 新 tokens。

Time to first token 包括 queueing、retrieval、prompt work 和 initial generation。End-to-end time 一直計至 response 結束。Inter-token timing 描述後續 output speed。

Throughput 衡量每單位時間完成的有用工作。透過 batching 改善 throughput，可能改變 latency 和 memory use；因此聲稱 serving 改善前，要先定義 workload。

建立對機制的理解

一個簡單 capacity consistency check

在穩定情況下，若平均 arrival rate 為每秒兩個 requests，平均 time in system 為三秒，Little's law 表示 system 內平均有六個 requests。

這不會決定安全 worker count，也不能預測 p95 latency。Variation、saturation、scheduling、batching 和 failures 仍很重要。

把 arithmetic 當作 consistency check，然後以有代表性的 input/output lengths 執行實測 load experiment。

建立對機制的理解

實驗與 release dependencies

Tracking tools 可儲存 runs、parameters、metrics 和 artifacts。在採用 service 前，一份小型 structured JSON record 已足夠學習概念。

按改變的 dependencies 選擇 checks。Prompt edit 需要 behavioral evaluation；embedding migration 需要 retrieval compatibility 和下游 tests。

保持 training 與 serving templates 一致。Evaluation 用一個 prompt/chunker，serving 卻用另一個，即使 source model 沒變，仍會產生 mismatch。

建立對機制的理解

實例練習與學習檢查

執行 local API，驗證 scoped citations，並記錄實際 end-to-end timings。然後整合所選真正 model，再測一次，交代 lengths、concurrency、warm/cold state 和 failures。

建立 manifest，故意測試 mismatch。從乾淨 directory 重現一次 evaluation。

當另一個人能識別運行中的 release、按 contract invoke，並區分實測 performance 和建議 deployment plan，就已準備好。
