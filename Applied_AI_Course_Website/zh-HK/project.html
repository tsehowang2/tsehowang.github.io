Capstone 開始之前

第 1–16 週專注理解及訓練小型 transformer。第一學期沒有應用交付里程碑。請以學習筆記記錄 shape、計算及 tiny-model 實驗。

應用要解決的問題

由第 17 週開始，為一小批公開技術文件建立助手。它應該在有證據支持時引用來源作答、區分版本、承認證據不足，並在有需要時使用可執行 tool。先使用虛構的 Atlas fixture，再選擇重用條款清晰的公開文件。

例如，一個 request 可能同時詢問 version 2 的 timeout 及總 retry delay。Retrieval 提供文件記載的設定；calculator 負責算術。保留版本資訊，並引用來源。

里程碑

  • 第 17 週：task charter、獲准使用的 corpus、問題類型與成功準則；比較 lexical 和 semantic search。
  • 第 18 週：持久儲存 vector、metadata、更新、刪除及 version filtering。在學 ANN 前先理解 exact search。
  • 第 19 週：retrieve、pack、generate 及 cite，由學校手冊例子開始。
  • 第 20 週：在固定 context budget 下，做一個受控 chunking 或 hybrid-retrieval 實驗。
  • 第 21 週：development protocol 與獨立 held-out 問題；分開記錄 retrieval 及答案錯誤。
  • 第 22–23 週：資源 budget 及實際量度的 profiling 實驗。
  • 第 24 週：診斷錯誤需要更好的證據、prompting 還是 supervised example；審核 target。
  • 第 25–26 週：LoRA 小規模試驗及 base／prompt／adapter 比較；負面結果也可以接受。
  • 第 27 週：calculator 加上一個文件／設定 tool、具型別的 argument 及受限制的權限。
  • 第 28 週：比較固定 workflow 與有界 model planner，保留完整 trace 及失敗記錄。
  • 第 29 週：API 與一致完整的 release manifest。
  • 第 30 週：regression check、observability、惡意輸入及 rollback 演練。
  • 第 31 週：整合 evaluation，示範有支持證據／證據缺失／錯誤版本／tool／失敗情況。
  • 第 32 週：為選定的 release 作答辯，並從乾淨目錄重現成果。

Evaluation 設計

建立至少 40 個經獨立核對的 case，涵蓋 paraphrase、版本衝突、答案缺失及 tool request。這只是實習最低要求，並非統計上有定論的 benchmark。把相關變體分組，防止近乎重複的內容造成 leakage。調整系統時可以查閱 reference corpus，但須保留最終問題及 label，不可用於 tuning。

量度 evidence recall、answer correctness、citation support、版本錯誤、refusal、tool argument、latency、token 及失敗。儲存每個 task 的輸出，並比較同一批 task。分清 simulation 與真實 model 量度。報告 uncertainty 及 task set 的限制。

交付項目及評分準則

提交 source、設定指引、corpus manifest、dataset card、實驗記錄、原始 evaluation 輸出、release manifest、demo 及報告。評分：task／data 定義 15；baseline／retrieval 20；evaluation／error analysis 25；tool／controller 15；reproducibility／operations 15；解讀／限制 10。

誠實的 portfolio 描述應指出：這是獨立建立的 prototype，並在指定 task set 上取得實際量度結果。不要虛構 production 用戶或 deployment。解釋為甚麼採用或不採用 retrieval、adapter 和 agent。

Release 與事故演練

Release 前，確認不可變的 manifest、corpus／index 相容性、model／tokenizer／adapter、prompt、tool 及環境。執行 deterministic test、integration check 及計劃中的 task evaluation。檢查錯誤版本證據、citation、未知 request、惡意文件內容、無效 tool argument、loop 額度耗盡及失敗回應。核對原始輸出及數值 denominator。為每項必要門檻記錄 pass／fail。

在指定長度及 concurrency 下量度 warm／cold end-to-end latency，並包含失敗。核實 API limit、適用的 caller 存取權、log 沒有 secret、source／update／deletion 的傳播，以及有 cache 時的 scope-aware cache 行為。儲存上一個合格 manifest 及已測試的還原程序。

演練時，故意指向錯誤 corpus hash 或不相容 index。觀察受控拒絕、還原上一版本，再執行 smoke request。不要修改唯讀 source corpus 來模擬；改用 manifest 副本或暫時 test fixture。

事故報告欄位：觸發原因／時間；用戶影響；受影響版本；偵測訊號；診斷證據；緩解措施；root cause；促成因素；一個 regression test；一項可量度的預防行動；負責人及跟進條件。演練失敗是需要修補的發現，不應隱瞞。
